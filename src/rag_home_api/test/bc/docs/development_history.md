# RAG 파이프라인 개발 이력: 변경 내용과 지표 변화

정리 기준일: 2026-11-26

이 문서는 기존 Markdown과 실제 측정 기록을 연결한 팀 공유용 종합 문서다.
무엇을 고민했고, 어떤 코드를 어떻게 바꿨으며, 어떤 조건에서 수치가 달라졌는지 정리한다.
문서 작성 과정에서 검색·생성·평가 API를 새로 호출하지 않았다.

## 1. 버전 이름과 비교 기준

서로 다른 종류의 이름이 섞여 있으므로 다음과 같이 구분한다.

| 이름 | 뜻 | 주의할 점 |
| --- | --- | --- |
| 청킹 V0 | 거래의 상세 본문을 임베딩 | 현재 선택한 청킹 |
| 청킹 V1 | 같은 상세 본문에 검색용 요약 추가 | 필터 개선 v1과 다른 이름 |
| small / large | 임베딩 모델 크기 | 생성 모델 크기가 아님 |
| A / B / C | Vector / Hybrid / Hybrid+reranker 검색 방식 | 순차 개발 버전이 아니라 비교 가능한 검색 구성 |
| 초기 필터(v1) | 자연어 조건 추출과 공통 필터를 연결한 첫 개선 단계 | 청킹 V0를 그대로 사용 |
| 정규화 보완(v2) | 초기 필터의 명칭·정보 요청·면적 처리 보완 | 청킹 V1로 바꾼 것이 아님 |
| 단계 0~8 | 이 문서에서 개발 과정을 설명하기 위한 번호 | 실제 Git 태그나 릴리스 번호는 아님 |

Hit@5는 상위 5개 안에 모든 참고 조건을 충족하는 거래가 최소 하나 있는 문항의 비율이다.
Dev는 근거 있는 8문항, 기존 Test는 T01~T17의 17문항을 분모로 삼는다.
신규 Test는 T21~T37의 다른 17문항이다. 각 질문셋의 근거 없는 문항은 별도 검토한다.
확인 요청으로 검색하지 않은 근거 있는 문항도 Hit@5 분모에서 빼지 않는다.

## 3. 단계 0: V0/V1과 small/large 비교

### 코드에서 달라진 부분

- [structural_chunk_v0.py](../structural_chunk_v0.py)의 `load_and_clean`, `row_to_text`, `create_documents`:
  거래 컬럼을 정제하고 지역·주택 정보·계약·금액의 상세 본문과 숫자 메타데이터를 생성한다.
- [structural_chunk_v1.py](../structural_chunk_v1.py)의 `add_search_columns`:
  지역·유형·가격 등을 조합한 검색용 요약을 추가한다. 단순히 청크 길이만 바꾼 실험이 아니다.
- 임베딩은 `text-embedding-3-small`과 `text-embedding-3-large`를 비교했다.

### 수치와 선택 이유

| 조합 | Dev Hit@5 | MRR@5 | 본문 입력 토큰 | 당시 1회 임베딩 추정 비용 |
| --- | ---: | ---: | ---: | ---: |
| V0/small | 3/8 (37.5%) | 0.375 | 5,168,969 | $0.1034 |
| V0/large | 2/8 (25.0%) | 0.250 | 5,168,969 | $0.6720 |
| V1/small | 2/8 (25.0%) | 0.150 | 7,380,407 | $0.1476 |
| V1/large | 3/8 (37.5%) | 0.208 | 7,380,407 | $0.9595 |

당시 기록된 비용 추정이며 현재 가격표가 아니다. 네 조합 모두 같은 CSV·Dev 질문을 사용했다.
V1/large는 Hit@5가 같아도 MRR이 낮고 비용이 높았다. 사전 선택 기준인 Hit@5→MRR→비용에 따라
V0/small을 유지했다. 이 작은 Dev 결과로 큰 모델이나 요약이 항상 불리하다고 일반화하지 않는다.

## 4. 단계 1~2: 초기 검색 구성에서 교안 구성으로

| 항목 | 초기 Mac 실험 | 교안 Windows 기준선 |
| --- | --- | --- |
| 청킹·임베딩 | V0/small | V0/small 유지 |
| A | Vector 상위 5개 | Vector 상위 5개 |
| B | Vector 20 + Kiwi BM25 20, 직접 RRF | Vector 20 + text.split BM25 20, EnsembleRetriever |
| C | 결합 후보 최대 20개, gpt-6-luna reranker | 결합 후보 최대 20개, Dongjin-kr/ko-reranker |
| 최종 문맥 수 | 최대 5개 | 최대 5개 |
| 기존 Test A | 6/17 (35.3%) | 6/17 (35.3%) |
| 기존 Test B | 5/17 (29.4%) | 7/17 (41.2%) |
| 기존 Test C | 8/17 (47.1%) | 10/17 (58.8%) |

현재 코드는 [lesson_pipeline.py](../lesson_pipeline.py)의 `build_retrievers`, `cross_encoder_model`에 모여 있다.
BM25 토큰화·결합 구현·reranker뿐 아니라 실행 환경·색인 실행도 다르므로 위 차이를 단일 변경의 효과로 분리하지 않는다.
이후 필터·정규화의 단계별 비교는 같은 Windows 기준선과 같은 질문셋을 사용한다.

초기에는 조건에 맞는 거래가 데이터에 있어도 검색 상위에 없어서 답하지 못하는 경우가 많았다.
예를 들어 ‘보증금 이하·면적 이상’은 의미 유사도만으로 수학적 비교가 보장되지 않았다.
또 reranker는 앞단 후보에 없는 정답 거래를 새로 찾아올 수 없었다.
이에 모델 확대보다 검색 후보를 조건으로 제한하는 개선을 우선했다.

## 5. 단계 3: 자연어 조건 추출과 메타데이터 필터

### 어디를 어떻게 수정했나

| 처리 | 파일·함수 | 기존 | 변경 |
| --- | --- | --- | --- |
| 조건 추출 | [query_filters.py](../query_filters.py) `EXTRACTION_PROMPT`, `build_filter_extractor` | 질문을 그대로 검색 | 질문의 지역·금액·면적·층·연도를 JSON 조건으로 추출 |
| 출력 검증 | 같은 파일 `parse_filter_plan` | 검색용 조건 객체 없음 | 허용 키·필드·연산자·유한 숫자·원문 source_text 검사 |
| 필터 검증 | [metadata_filters.py](../metadata_filters.py) `validate_filter` | 필터 없이 전체 검색 | 문자열 일치와 숫자 비교 연산자의 허용 범위를 제한 |
| Vector 필터 | [lesson_pipeline.py](../lesson_pipeline.py) `build_retrievers` | 전체 DB에서 유사도 검색 | `search_kwargs`에 PGVector `filter` 전달 |
| BM25 필터 | 같은 함수, `matches_filter` | 전체 본문을 BM25 색인 | 같은 조건을 통과한 로컬 문서만 BM25 색인 |
| 처리 분기 | [query_filters.py](../query_filters.py) `execute_query` | 검색 후 답변 흐름 중심 | 확인 요청·미지원 요청을 검색 전에 구분 |
| 빈 결과 | [lesson_pipeline.py](../lesson_pipeline.py) `build_chain` | 근거 탐색·생성 흐름 | 빈 결과이면 조건을 풀지 않고 안내, 답변 LLM 생략 |

예를 들어 ‘남현동 빌라 전세, 2억 5천만원 이하, 8평 이상’은 다음 필터로 구조화한다.
아래는 동작 설명용 예시다.

```json
{
  "region_dong": "남현동",
  "housing_type": "연립다세대",
  "lease_type": "전세",
  "deposit_manwon": {"$lte": 25000},
  "area_pyeong": {"$gte": 8}
}
```

조건은 같은 거래가 전부 만족해야 한다. Vector만 필터링하고 BM25를 그대로 두면
Hybrid에서 조건 밖 거래가 다시 섞일 수 있어 두 검색 경로에 같은 필터를 적용했다.

### 수치는 어떻게 달라졌나

| 질문셋·구성 | 교안 기준선 | 초기 필터(v1) | 변화 |
| --- | ---: | ---: | ---: |
| Dev A | 3/8 | 6/8 | +3문항, +37.5%p |
| Dev B | 4/8 | 6/8 | +2문항, +25.0%p |
| Dev C | 4/8 | 6/8 | +2문항, +25.0%p |
| 기존 Test A | 6/17 | 12/17 | +6문항, +35.3%p |

조건 추출·공통 필터·확인 요청을 함께 추가한 결과다. 각각의 단독 효과를 분리한 실험은 아니다.
문서에 있는 D01~D04의 수동 필터 1/4→4/4는 별도의 사전 진단이며 이 전체 평가와 구분한다.

## 6. 단계 4: 질문을 과거형으로 바꾼 시도

과거 거래를 검색한다는 점에서 ‘찾고 있어요/있나요’를 ‘찾고 있었어요/있었나요’로 바꿔 보았다.
숫자·명칭·정답 조건은 유지하고 ‘과거 거래’ 같은 검색 단어를 새로 추가하지 않았다.

| 실험 | 기존 Test A | 기존 Test B | 기존 Test C |
| --- | --- | --- | --- |
| 필터 없는 원본 검색, 현재형→과거형 | 6/17→6/17 | 7/17→7/17 | 10/17→10/17 |
| 초기 필터, 필터 고정 후 검색 문장만 과거형 | 12/17→12/17 | 12/17→12/17 | 12/17→12/17 |
| 초기 필터, 과거형에서 조건 재추출 | 12/17→12/17 | 12/17→12/17 | 12/17→12/17 |

검색 순서·문서 목록이 바뀌어도 적중률 상승은 없었다. 이 시도를 최종 필수 리라이트 구현으로 채택하지 않고,
실패 원인이 더 명확했던 이름·조건 해석 개선을 우선했다. 모든 리라이트 방법이 효과 없다는 결론은 아니다.

## 7. 단계 5: 정규화 보완(v2)

### 어떤 실패를 어떤 규칙으로 보완했나

| 문제·대표 문항 | 수정 위치 | 보완한 동작 |
| --- | --- | --- |
| T02 ‘단독·다가구’와 원본 유형 불일치 | `canonical_housing_type`, `parse_filter_plan` | 공백·문장부호를 정리해 단독다가구 등 원본 유형으로 통일 |
| T13 비슷한 이름에 서로 다른 유형 존재 | `resolve_building_plan` | 지역·주택 유형으로 먼저 후보를 좁힌 뒤 건물 이름 비교 |
| T15 ‘대창센시티 2차’ 약칭 | 같은 함수 | 단지·차수 번호를 보존한 유일 원본 후보만 연결 |
| T17 공백·오피스텔 접미사 차이 | `compact_name`, `resolve_building_plan` | 정규화 후 유일한 원본 이름으로 매핑 |
| T16 ‘보증금은 얼마인지’까지 제한으로 처리 | `supported_information_request` | 단순 정보 요청과 실제 검색 제한 구분 |
| T16 정확한 ㎡와 약 평수의 중복 등식 | `parse_filter_plan` | 환산상 일치하면 정확한 ㎡ 유지, 근삿값 평수의 중복 일치 조건 제거 |
| 실제 제약을 정보 요청으로 제거할 위험 | `supported_information_request` | ‘무보증·저렴한·이하’ 등은 단순 정보 요청으로 없애지 않음 |

관련 구현은 [query_filters.py](../query_filters.py)에 있다. 금액의 자연어 단위 해석은 추출 프롬프트·LLM이 수행하고,
유형·건물명·중복 면적 조건 보정은 프로그램 로직도 수행한다. 모든 처리가 정규식만으로 구현된 것은 아니다.
보정 이력은 `FilterPlan.normalizations`에 남긴다.

후보가 여러 개이거나 면적이 모순되면 추측해서 하나를 고르지 않고 확인 요청을 유지한다.
Dev D08의 ‘5평 후반대’도 구체적인 범위를 확인하도록 남겼다.

### 수치는 어떻게 달라졌나

| 질문셋 | 초기 필터(v1) | 정규화 보완(v2) | 변화 |
| --- | ---: | ---: | ---: |

| 기존 Test A/B/C 각각 | 12/17 (70.6%) | 17/17 (100.0%) | +5문항, +29.4%p |

T02·T13·T15·T16·T17이 기존 질문에서 회복됐다. 청킹 V0·small·검색 후보 수·RRF·reranker 설정은 유지했다.
이미 본 Test를 분석해 보완했으므로 이 17/17은 회귀 평가다.
후속 정보 요청 경계 보호는 저장된 실제 추출 JSON 30개를 재처리해 필터·분기가 같음을 확인한 검증이며,
API를 다시 실행한 새 성능 측정은 아니다.

## 8. 기존 질문에서 검색 품질이 변한 전체 모습

### 같은 Windows 비교 안에서 본 Hit@5

| 질문셋·구성 | 교안 기준선 | 초기 필터 | 정규화 보완 | 기준선→보완 |
| --- | ---: | ---: | ---: | ---: |
| Dev A | 3/8 | 6/8 | 7/8 | +50.0%p |
| Dev B | 4/8 | 6/8 | 7/8 | +37.5%p |
| Dev C | 4/8 | 6/8 | 7/8 | +37.5%p |
| 기존 Test A | 6/17 | 12/17 | 17/17 | +64.7%p |
| 기존 Test B | 7/17 | 12/17 | 17/17 | +58.8%p |
| 기존 Test C | 10/17 | 12/17 | 17/17 | +41.2%p |

### 같은 설정으로 재평가한 RAGAS

아래는 저장된 최초 Mac 실험과 정규화 보완 후 문맥을 이번에 같은 평가 설정으로 재채점한 값이다.
과거 보고서의 RAGAS 평균에 개선 후 값만 이어 붙인 표가 아니다.

| 구성 | 초기 Context Precision | 개선 후 | 차이 | 초기 Context Recall | 개선 후 | 차이 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| A | 0.2718 | 1.0000 | +0.7282 | 0.3235 | 0.9804 | +0.6569 |
| B | 0.1554 | 1.0000 | +0.8446 | 0.3361 | 1.0000 | +0.6639 |
| C | 0.4706 | 1.0000 | +0.5294 | 0.4559 | 1.0000 | +0.5441 |

각 단계 A/B/C × 17문항, 총 102개 입력을 평가했다. C의 전체 개선에는 앞서 설명한 검색 구성 변경도 포함된다.
과거 최초 보고서의 Recall은 A 0.778, B 0.662, C 0.787이었다. 이번 초기 재채점 값과 섞어 차이를 계산하지 않는다.
점수 차이의 해석에는 평가 설정·참고 정답·LLM 심사 변동을 고려해야 한다.
출처: 실측 비교(개인 기록, 저장소 미포함), 지표 점검(개인 기록, 저장소 미포함).

### F1은 무엇을 계산했나

| 구성 | 초기 문서 Precision | 개선 문서 Precision | 초기 집합 Recall@5 | 개선 집합 Recall@5 | 초기 집합 F1@5 | 개선 집합 F1@5 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| A | 0.2353 | 1.0000 | 0.0832 | 0.2481 | 0.0948 | 0.3370 |
| B | 0.1412 | 1.0000 | 0.0576 | 0.2481 | 0.0627 | 0.3370 |
| C | 0.3059 | 1.0000 | 0.0926 | 0.2481 | 0.1113 | 0.3370 |

이 표는 원본에서 모든 조건을 충족하는 거래 전체를 정답 집합으로 본 결정적 채점이다.
문서 Precision은 반환 거래 중 적합 비율, 집합 Recall은 전체 적합 거래 중 반환 비율이다.
F1은 질문별 두 값의 조화평균을 계산한 뒤 평균한다. RAGAS Context Recall과 분모가 다르다.
정답 거래가 수백 건이어도 최대 5개만 반환하므로 집합 Recall과 F1이 1.0에 도달하지 않을 수 있다.

## 9. 단계 6: 캐싱 추가

### 무엇을 수정했나

[cached_pipeline.py](../cached_pipeline.py)를 추가했다.

| 위치 | 동작 |
| --- | --- |
| `ResponseCache.get/put` | TTL 600초·최대 100개, 만료 제거와 LRU 교체 |
| `runtime_version` | 실행 코드·CSV·잠금 파일 변경을 캐시 키에 반영 |
| `CachedPipeline.answer` | 조건 추출 전에 조회, miss 시 기존 파이프라인 실행, 성공·근거 있는 응답 저장 |
| 캐시 키 | 질문·사용자/세션 범위·색인 버전·A/B/C·실행 설정 버전 구분 |
| 저장 값 | 답변과 실제 출처를 함께 보존. 반환값을 복사해 캐시 원본 보호 |

적중 시 조건 추출·검색·재정렬·생성을 생략한다. 오류·빈 검색 결과·확인 요청·미지원 응답은 저장하지 않는다.
데이터·DB 색인 변경 시 호출자가 `index_version`을 갱신해야 한다.
현재는 단일 프로세스 메모리 캐시이며 API·FE를 구현한 것이 아니다.

### 검증 수치와 미측정 항목

| 항목 | 확인한 값·상태 |
| --- | --- |
| 저장 결과 주입 15건 | 최초 5건 miss, 동일 질문 5건 hit, 버전 변경 5건 miss |
| 파이프라인 대역 호출 | 15요청 중 10회, hit 5건은 호출 생략 |
| 답변·출처 보존 | 캐시 전후 동일 |
| 경계 조건 | TTL·LRU·scope 분리·복사 보호·오류 비저장 확인 |
| 실제 모델 포함 응답 시간 절감 | 아직 실측 결과 없음 |
| 실제 API 청구 비용 절감 | 아직 실측 결과 없음 |

캐시 때문에 Hit@5나 Context Precision이 추가 상승했다고 쓰지 않는다.
최적화의 목적은 같은 요청의 중복 처리를 줄이는 것이고 실제 속도·비용 효과는 별도 실측 대상이다.
선택 이유: 캐싱 선택 문서(개인 기록, 저장소 미포함). 구현·검증 상세: 캐싱 및 품질 비교(개인 기록, 저장소 미포함).

## 10. 단계 8: 신규 T21~T40으로 확인한 한계

동일한 검색 코드를 유지하고 C 구성·캐시 끔으로 신규 20문항을 실행했다.
정답·허용 근거는 검색·생성 입력에 넣지 않고 사후 채점에 사용했다.

| 항목 | 결과 |
| --- | --- |
| 근거 있는 17문항 Hit@5 | 15/17 (88.2%) |
| 반환 거래의 조건 검사 | 66개 모두 조건 충족 |
| 미적중 | T31·T33 |
| T31 | 관악 현대 ↔ 현대(관악): 단어 순서 차이를 연결하지 못해 확인 요청 |
| T33 | 서울대입구 코업레지던스 ↔ CO-OP RESIDENCE/서울대입구: 한글·영문 표기를 연결하지 못해 확인 요청 |
| 근거 없는 문항 | T38은 미지원 정보 안내, T39·T40은 검색 결과 없음 안내 |
| 신규 질문 RAGAS | 이번 실행에서 측정하지 않음 |

T31·T33은 금액·면적 등 숫자를 추출했지만 건물명 연결에서 멈췄다.
현재는 이 결과를 보고 검색 코드를 다시 수정하지 않았으며, 추가 보완 시 별도 후속 실험으로 구분한다.
근거 없는 3문항의 원본 응답은 확인했지만 독립적인 팀원 교차 검토 점수와는 구분한다.

기존 질문 17/17과 신규 질문 15/17은 서로 다른 질문셋이다.
같은 질문에서 코드 변경으로 100%→88.2%로 하락한 것이 아니라, 더 넓은 표현에서 한계를 확인한 것이다.
이 실행 이후 T21~T40은 더 이상 미사용 평가셋이 아니다.
근거: 신규 질문 결과(개인 기록, 저장소 미포함).

## 11. 현재 상태와 팀에 전달할 내용

최종 실행 흐름은 **V0/small → 조건 추출·검증 → 정규화 → 필터 적용 A/B/C → 근거 답변**이다.
캐시를 사용하려면 이 흐름을 감싸는 `CachedPipeline.answer()`를 호출한다.
A/B/C는 `lesson_pipeline.py` 안에 모두 구현돼 있고 `system` 인자로 선택하며 기본은 C다.
V1은 대안을 시도한 작업 근거로 남겨두었다.

| 구분 | 상태 |
| --- | --- |
| 청킹·임베딩 선택 | V0/small 선택 근거 확보 |
| 조건 추출·필터·정규화 | 구현 및 기존 질문 회귀 평가 완료 |
| 캐시 | 구현·저장 결과 재생 검증 완료, 실제 지연·비용 측정은 남음 |
| 기존 질문 RAGAS | 초기/개선 102개 입력 재평가 완료 |
| 신규 질문 | C 실행 20건, Hit@5 15/17, 건물명 한계 확인 |
| T16 반복 심사 | 실행기 준비, 실제 반복 측정 결과 없음 |
| API·FE | 팀 대표 담당, 이 작업 범위에서 구현하지 않음 |

발표에서는 ‘처음에는 표현력 개선을 시도했지만 숫자 조건 검색이 병목이어서,
공통 필터를 연결하고 명칭·조건 해석을 보완했다. 기존 질문에서는 개선됐고,
신규 질문에서는 한글·영문과 단어 순서 차이가 남았다’는 흐름으로 설명할 수 있다.
