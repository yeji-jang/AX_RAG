# 검색 품질 개선 과정과 비교 결과

2026-11-25~26 작업 기록. 원본: HTML 비교 문서(5MB, 저장소 미포함).
HTML 본문과 내장 실행 기록을 바탕으로 팀 공유에 필요한 방법·수치·판단을 정리했다.
이번 문서 작성에서는 검색·생성 API나 DB를 다시 실행하지 않았다.

## 1. 무엇을 고민했나

부동산 질문은 의미가 비슷한 문서를 찾는 것뿐 아니라 지역·전월세·보증금·월세·면적 조건을 모두 충족해야 한다.
기존 Vector/Hybrid 검색은 관련 거래를 가져와도 숫자 범위와 유형을 어기는 경우가 있었다.
이에 다음 가설을 순서대로 확인했다.

1. 자연어 조건을 추출해 검색 전에 필터링하면 조건 일치 근거를 더 잘 찾을 수 있는가?
2. 데이터가 과거 거래이므로 질문을 과거형으로 바꾸면 검색이 개선되는가?
3. 필터 도입 후 남는 실패를 건물명·유형·면적 표현의 정규화로 줄일 수 있는가?

## 2. 실험 조건과 지표

| 항목 | 설정 |
| --- | --- |
| 데이터 | 과거 공공 거래 CSV 31,772건 |
| 데이터 기간 | 2025-11-24~2026-11-20 |
| 청킹·임베딩 | V0, 거래당 1청크, text-embedding-3-small, 1,536차원 |
| 질문 | 기존 Dev 10개 + 기존 Test 20개 |
| Hit@5 분모 | 과거 참고 근거가 있는 Dev 8개, 기존 Test 17개 |
| A | Vector 상위 5개 |
| B | Vector 20개 + BM25 20개, text.split(), EnsembleRetriever, RRF c=60, 가중치 0.5:0.5 |
| C | 결합 후보 최대 20개 → Dongjin-kr/ko-reranker, max_length=512 → 상위 5개 |
| 답변 모델 | gpt-6-luna |
| 기준선 | 커밋 24d3290의 원본 교안 코드를 Windows에서 재실행 |

**Hit@5**는 상위 5개 안에 질문의 참고 조건을 모두 만족하는 거래가 하나 이상 검색된 문항의 비율이다.
근거 없는 5문항은 Hit@5 분모에서 제외한다. 확인 요청·오류·누락도 근거 있는 문항에서는 분모에 포함한다.

같은 Windows DB·임베딩·기존 질문으로 비교했다. 아래의 초기 필터(v1)·정규화 보완(v2)는
**필터 파이프라인의 개선 단계**이며, `structural_chunk_v0.py`/`structural_chunk_v1.py`의 청킹 버전과 다르다.
이 비교에서 청킹은 계속 V0를 사용했고 본문 재임베딩도 하지 않았다.

## 4. 첫 번째 시도: 검색 전에 조건 필터 적용

기존 흐름은 질문으로 전체 데이터에서 Vector/BM25 검색을 한 뒤 RRF·reranker·답변 생성으로 이어졌다.
개선 흐름은 먼저 질문의 조건 JSON을 추출·검증하고, 조건을 만족하는 후보 안에서 같은 검색·재정렬을 수행한다.

| 변경 | 내용 | 관련 실행 코드 |
| --- | --- | --- |
| 조건 추출 | 지역·전월세·예산·면적·층·건축연도를 구조화 | `query_filters.py` |
| 필터 검증 | 허용 필드·유한 숫자·연산자 검사, 금액·주택 유형 정리 | `metadata_filters.py`, `query_filters.py` |
| 양쪽 검색에 필터 적용 | PGVector filter와 BM25 로컬 후보에 동일 조건 적용 | `lesson_pipeline.py` |
| 모호한 조건 처리 | 해석이 불명확하면 검색 전에 확인 요청 | `query_filters.py` |
| 빈 결과 처리 | 조건을 임의로 풀지 않고 안내, 답변 LLM 호출 생략 | `lesson_pipeline.py` |
| 정보 부족 처리 | 관리비·주차 등 자료에 없는 요청을 안내 | `query_filters.py` |

초기 필터만으로 Dev는 A/B/C 각각 6/8, 기존 Test는 각각 12/17이 됐다.
이 변화는 조건 추출·사전 필터·확인 요청 처리를 함께 추가한 결과다. 각 변경의 효과를 따로 분리한 실험은 아니다.

조건 추출 프롬프트도 같은 원칙으로 보완했다. 원본 CSV·청킹·임베딩·후보 수·BM25·RRF·reranker·생성 모델·질문·정답 기준은 유지했다.
건물 후보가 여러 개이거나 면적이 모순되면 확인 요청을 유지한다. 질문별 정답 거래 ID를 검색 조건에 넣는 방식이 아니다.

Dev에서 남은 **D08의 ‘5평 후반대’**는 임의의 범위로 단정하지 않고 사용자에게 범위를 확인하도록 남겼다.
그 결과 정규화 보완 후 Dev는 7/8, 기존 Test는 17/17이다.

측정 후에는 ‘보증금 없는 집’, ‘월세가 저렴한 집’처럼 실제 제약인 표현을 단순 정보 요청으로 제거하지 않는 경계 보호도 추가했다.
HTML 기록에 따르면 저장된 조건 JSON 30개를 최종 코드로 재처리했을 때 필터·처리 경로는 같았다.
이 검증은 API를 다시 호출한 새 성능 측정과 구분한다.

## 8. 팀 코드 통합과 FE 연동에 이어갈 내용

최종 실행 경로는 V0/small에 자연어 조건 추출·정규화·Vector/BM25 공통 필터를 적용한 구성이다.
`structural_chunk_v1.py`는 청킹 대안을 시도한 구현으로 별도 보관한다.
채팅 API는 조건 추출과 `execute_query`를 호출하고 FE에 답변·처리 상태·출처를 전달하는 연결 지점이 된다.
HTTP API·대화 이력은 이 비교에서 구현하거나 검증한 범위가 아니다.

현재 폴더에서는 재현용 평가 실행기·채점 코드·검증 테스트·별도 결과 JSON·보고서 생성기를 제외했다.
HTML 안의 과거 실행 파일명·코드 스냅샷·경로는 측정 당시 이력이다. 현재 실행 방법은 [상위 README](../README.md)를 따른다.

## 9. 결과 해석의 범위

- 기존 질문을 분석해 보완한 회귀 평가이며, 새 최종 Test T21~T40은 사용하지 않았다.

- 이 데이터로는 현재 입주 가능한 매물·현재 호가를 확인할 수 없다.
- 이번 수치는 HTML에 보관된 실행 기록이며, Markdown 작성 시 새 성능 측정을 하지 않았다.
