## 2. 왜 검색이 안 될까? (원인 3가지)

### 원인 1. 임베딩과 BM25는 숫자·범위 조건(`이하`, `이상`)을 비교하지 못함
부동산 검색 질의의 핵심은 대부분 부등호/범위 조건입니다.
- 예: `T01` — *"신림동에서 보증금 300만원 이하, 월세 40만원 이하인 자취방을 찾고 있어요. 4평 이상인 집이 있나요?"*
- 원본 CSV에는 이 조건을 모두 만족하는 거래가 **1,216건**이나 존재합니다.
- 그럼에도 **A/B/C 모두 Hit@5 미적중**이었고, A와 C의 상위 5개에는 `보증금 500~1,000만원`, `3.75평`(`좋은집`) 등 조건을 미세하게 벗어난 거래만 검색되었습니다.
- 텍스트 임베딩(`small`/`large`)과 키워드 검색(BM25)은 `"보증금"`, `"월세"`, `"평"` 같은 단어의 의미/빈도 유사도는 잡지만, **`<= 300` vs `500`**, **`>= 4평` vs `3.75평`** 같은 수치 대소 비교를 수행하지 못합니다.

### 원인 2. Hybrid(B)에서 Kiwi BM25가 오히려 성능을 깎아먹음 (`35.3% → 29.4%`)
미적중 질문의 **1위 근거가 위반한 조건**을 비교하면 B의 부작용이 명확히 드러납니다.

| 구성 | 건물명 | 건축연도 | **법정동** | 보증금 | 월세 | 평수 | 면적 | **전월세 구분** | **주택 유형** | 층 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| A (Vector) | 3 | 3 | **0** | 4 | 1 | 4 | 1 | **3** | **2** | 2 |
| B (Hybrid) | 4 | 2 | **10** | 4 | 0 | 3 | 1 | **7** | **8** | 4 |
| C (Rerank) | 3 | 1 | **0** | 4 | 1 | 2 | 0 | **3** | **1** | 1 |

- Vector(A)에서는 `법정동` 위반이 **0건**이었지만, Hybrid(B)에서는 **10건**으로 급증했고 `주택 유형`(8건), `전월세 구분`(7건) 위반도 크게 늘었습니다.
- 실제로 `T01 · B`에서는 **"신림동"**을 찾는데 1위로 **"남현동 / 보증금 20,000만원 / 월세 3만원"** 거래가 올라왔습니다.
- **코드상 원인 (`retrieval_experiment.py`):**
  - `build_keyword_index()`가 모든 청크에 공통으로 들어 있는 필드 라벨(`자치구:`, `법정동:`, `주택 유형:`, `월세:`, `보증금:` 등)을 포함한 문서 전체를 그대로 `BM25Okapi`로 색인합니다.
  - `fuse_rrf()`가 Vector 20개와 BM25 20개를 `1:1` 동일 가중치(`1 / (60 + rank)`)로 합산하면서, BM25의 부정확한 상위 결과(동/유형 불일치)가 Vector 결과를 밀어내고 상위 20개 후보를 오염시켰습니다.

### 원인 3. Reranker(C)는 후보 20개 안에 정답이 없으면 복구 불가
- `C`는 `B`가 만든 결합 후보 **20개(`CANDIDATES = 20`)**만 `gpt-6-luna`로 재정렬합니다.
- LLM Reranker가 숫자 조건을 비교해 순위를 끌어올리는 효과(`29.4% → 47.1%`)는 있지만, 앞단(Vector + BM25)에서 정답 거래가 20위 안에 들지 못하면 Reranker도 찾을 수 없습니다.

## 3. 어떻게 개선해야 할까?

### 1순위: 질의 → 메타데이터 필터 추출 + DB `WHERE` 필터링 (Self-Querying)
이미 [structural_chunk_v0.py](../structural_chunk_v0.py)에서 DB에 정제된 메타데이터 컬럼을 저장하고 있으므로, **자연어 질문에서 조건을 먼저 구조화(JSON)해 DB 필터로 거른 뒤 벡터 검색을 수행**하는 것이 가장 확실한 해결책입니다.

#### 이미 검증된 효과 (`check_metadata_filter.py`)
Dev 직접 검색 4문항(`D01`~`D04`)에 대해 메타데이터 필터 적용 전후를 비교한 결과:

| 문항 | 조건 요약 (허용 거래 수) | 필터 전 Hit@5 | 필터 후 Hit@5 | 필터 후 상위 5개 전원 일치 |
| --- | --- | --- | --- | --- |
| D01 | 신림동, 월세, 보증금≤500, 월세≤45, ≥5평 (1,713건) | 1 | **1** | Yes |
| D02 | 봉천동, 오피스텔, 월세, 보증금≤1000, 월세≤70, ≥2018년, ≥5평 (30건) | 0 | **1** | Yes |
| D03 | 남현동, 연립다세대, 전세, 보증금≤25000, ≥8평 (23건) | 0 | **1** | Yes |
| D04 | 관악구, 아파트, 월세, 보증금≤5000, 월세≤120, ≥15평, ≥5층 (50건) | 0 | **1** | Yes |
| **합계** | **4문항** | **1/4 (25.0%)** | **4/4 (100.0%)** | **4/4** |

#### 구현 가이드 (4단계 파이프라인)

- **파이프라인 변경:**
  - **기존:** `질문 → Vector / BM25 → RRF → Reranker → 생성`
  - **개선:** `질문 → [1] 조건 JSON 추출 → [2] 메타데이터 필터 + Vector 검색 → [3] (선택) Reranker → 생성`

1. **LLM Structured Output으로 조건 JSON 추출**
   - 추출 대상 필드:
     - 문자열 일치: `region_gu`, `region_dong`, `housing_type`, `lease_type`
     - 범위 조건(`$lte`, `$gte`, `$eq`): `deposit_manwon`, `monthly_rent_manwon`, `build_year`, `floor`, `area_pyeong` / `area_m2`
   ```json
   // 예시: "남현동에서 빌라 전세를 알아보고 있어요. 2억 5천만원 이하에 8평 이상인 집이 있나요?"
   {
     "region_dong": "남현동",
     "housing_type": ["연립다세대"],
     "lease_type": "전세",
     "deposit_max": 25000,
     "area_pyeong_min": 8.0,
     "building_name": null
   }
   ```
2. **도메인 표현·단위 정규화**
   - 금액: `"2억 5천"` → `25000`(만원), `"천만원"` → `1000`(만원)
   - 주택 유형 동의어: `"빌라"` → `연립다세대`, `"자취방"`/`"원룸"`은 CSV상 `단독다가구`·`연립다세대`·`오피스텔`에 섞여 있을 수 있으므로 `housing_type` 필터를 강제하지 않거나 복수 허용(`$in`) 처리
   - 면적·층: `"5평 후반대"` → `area_pyeong_min: 5.5, area_pyeong_max: 6.0` / `"고층"` + `"10층 이상"` → `floor_min: 10`
3. **DB 검색 시 메타데이터 필터(`WHERE` / `PGVector filter`) 적용**
   - **방식 A (`psycopg` SQL 직접 사용 시):** 추출된 조건만 `WHERE` 절에 동적 조립 후 벡터 유사도로 정렬
     ```sql
     SELECT chunk_id, transaction_id, source_row, document, metadata,
            embedding <=> %s AS distance
     FROM bc_embeddings_v0_small
     WHERE metadata->>'region_dong' = '남현동'
       AND metadata->>'housing_type' = '연립다세대'
       AND metadata->>'lease_type' = '전세'
       AND (metadata->>'deposit_manwon')::int <= 25000
       AND (metadata->>'area_pyeong')::float >= 8.0
     ORDER BY distance, chunk_id
     LIMIT 5;
     ```
   - **방식 B (`PGVector` 사용 시):** `check_metadata_filter.py`(현재 삭제됨)처럼 `store.similarity_search(query, k=5, filter=...)`에 추출된 딕셔너리 전달
4. **실전 함정 3가지 방어**
   - **건물명(`building_name`)은 하드 필터(`=`)에서 제외:** `"e편한세상 1단지"` vs `"e편한세상1단지"`처럼 띄어쓰기·표기가 다를 수 있으므로, 지역·유형·예산 필터로 먼저 좁힌 뒤 **Vector 유사도** 또는 **`ILIKE` 부분 일치**로 상위에 올리는 것이 안전합니다.
   - **본문 전체 BM25 제거:** 메타데이터 필터가 동/유형/전월세를 100% 걸러주므로, 전체 문서를 BM25로 섞으면 노이즈만 생깁니다. 필터 후 **Vector 검색만** 쓰거나 후보 20개에 Reranker만 붙이는 편이 정확합니다.
   - **0건일 때 정직한 안내:** 필터 결과가 0건이면 억지로 비슷한 거래를 가져오지 않고 *"조건을 모두 만족하는 과거 거래가 없습니다"*로 응답합니다(`D09`, `D10` 등 근거 없음 문항 대응).

### 2순위: 임베딩/BM25/후보 수 조정 (보조 개선)
메타데이터 필터를 적용하기 어렵거나 필터 완화 후 재검색할 때를 위한 보조 개선점입니다.

1. **BM25 사용 방식 개선 (또는 제거)**
   - 메타데이터 필터가 동/주택유형/전월세 구분을 이미 처리해 준다면, 현 방식의 전체 본문 BM25 + `1:1` RRF는 오히려 노이즈가 될 수 있습니다.
   - 키워드 검색이 꼭 필요하다면 `building_name`, `region_dong` 등 핵심 고유명사 필드만 별도 검색하거나 RRF에서 Vector 가중치를 높여야 합니다.
2. **후보 수(`CANDIDATES`) 확대**
   - 필터 없이 검색하는 경로가 남아 있다면 `k=20`은 31,772건 중 조건 일치 매물을 찾기에 너무 작습니다. 후보 수를 `50~100`으로 늘린 뒤 프로그램 로직으로 수치 조건을 검증하고 Reranker에 넘기는 방식이 필요합니다.
3. **임베딩 모델 교체(`small → large`)나 청킹(`V0 → V1`) 변경은 후순위**
   - Dev 비교에서 `large` 모델이나 `V1` 요약 추가는 비용·저장 용량만 크게 늘리고 Hit@5(`25.0% ~ 37.5%`)를 개선하지 못했습니다.
   - **현재 병목은 표현력이 아니라 조건 필터링**이므로, `V0 + text-embedding-3-small`을 유지한 채 메타데이터 필터 파이프라인을 붙이는 것이 비용·성능 양면에서 가장 효율적입니다.
