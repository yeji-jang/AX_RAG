# 필수 최적화로 캐싱을 선택하는 이유

작성일: 2026-11-26

> 후속 구현: `cached_pipeline.py`에 캐싱을 구현했다. 실제 적용 내용과 저장 결과 기반
> 검증·지표, 외부 연결 제한으로 미측정한 항목은 [구현 및 품질 비교](./caching_and_quality_comparison.md)를 따른다.
> 아래는 구현 전 선택 근거와 제안 이력이다.

이 문서는 캐싱을 고른 근거와 구현 전 계획을 보존한다. **현재는 구현과 저장 결과 주입 검증까지 완료했고, 실환경 시간·비용 측정은 아직 없다.**
아래 예상 효과를 실제 측정 성과로 제시하지 않는다. 데이터 특성과 지표 해석은 [데이터·수치 안내](./data_and_metrics_guide.md), 현재 선택의 상세 근거는 [실험기록 §9](../실험기록.md#experiment-09)를 참고한다.

## 1. 현재 단계와 남은 필수 항목

현재 조건 추출·정규화·메타데이터 필터와 A/B/C 검색·답변 흐름은 구현되어 있다.
따라서 검색 파이프라인에 추가할 필수 최적화는 **캐싱 또는 쿼리 리라이트 중 하나**다.
캐싱을 선택하면 쿼리 리라이트를 추가로 구현할 필요는 없다.

다만 이는 최적화 항목의 범위다. 전체 프로젝트에는 실행 인터페이스, 최종 평가와 원본 기록,
팀 통합·시연 등 별도 필수 항목이 남는다. 이 문서는 그 작업을 완료했다고 간주하지 않는다.

| 현재 기능 | 역할 | 캐싱·리라이트 필수 항목과의 관계 |
| --- | --- | --- |
| 조건 추출·정규화 | 질문에서 지역·금액·면적 등 검색 조건을 구조화 | 메타데이터 필터를 위한 처리 |
| 메타데이터 필터 | Vector와 BM25에서 조건 밖 후보를 제외 | 조건 일치 검색 개선 |
| 과거형 질문 비교 | 시제만 바꾸어 적중률 변화를 관찰 | 리라이트의 전체 필수 검증을 완료한 것은 아님 |
| reranker의 `lru_cache` | 모델 객체를 재사용해 반복 로딩 방지 | 질문별 응답 캐시·버전 무효화 검증과 별개 |

## 2. 두 방법은 무엇을 개선하나

| 비교 항목 | 정확 일치 캐싱 | 쿼리 리라이트 |
| --- | --- | --- |
| 목적 | 같은 요청의 중복 연산·호출 줄이기 | 검색하기 좋은 질의로 질문 변환 |
| 동작 | 유효한 이전 답변·출처를 재사용 | 변환 질의를 실제 검색에 사용 |
| 현재 파이프라인에 미치는 영향 | 미적중 시 기존 흐름 그대로 실행 | 검색 질의가 달라져 후보·순위가 달라질 수 있음 |
| 주요 주의점 | 오래된 답변 재사용, 사용자 간 범위 혼동 | 금액·지역·유형 등 원질문 의도 변경 |
| 효과가 있는 요청 | 키가 같은 반복 요청 | 변환이 검색에 도움이 되는 요청 |
| 발제의 별도 검증 | 답변 가능 5문항 × 미적중·적중·버전 변경 = 15건 | 최종 20문항에 C와 C+리라이트 비교 |
| 추가 구현 | 키·저장·조회·TTL·무효화·기록 | 변환 프롬프트·의도 보존·오류 시 원질문 fallback·기록 |

캐싱 자체는 최초 질문의 검색 정확도를 높이지 않는다. 리라이트도 항상 정확도를 높이는 것은 아니다.

## 3. 현재 프로젝트에서 캐싱을 추천하는 이유

### 3.1 조건 검색을 개선한 현재 흐름을 유지할 수 있다

현재는 질문의 조건 추출과 원본 데이터 표기 정규화로 검색 실패를 줄였다.
정규화 보완 후 기존 질문의 Hit@5는 Dev 7/8, 기존 Test 17/17이다.
이는 이미 분석한 질문으로 보완한 회귀 평가이며 새로운 질문에 대한 성능 보장은 아니다.

이 상태에서 캐싱은 미적중 시 기존 검색 흐름을 그대로 실행하게 할 수 있다.
리라이트는 검색 질의를 새로 바꾸므로 조건 추출과 검색 질의 사이의 일관성도 함께 점검해야 한다.
필수 범위에 집중하고 팀 코드와 연결하려는 현재 목적에는 캐싱이 변경 범위를 작게 유지하기 좋다.

### 3.2 수행한 시제 변경 실험에서는 추가 검색 이득이 없었다

| 실험 | 관찰 결과 |
| --- | --- |
| 필터 없음: 현재형 → 과거형 | Dev·기존 Test에서 A/B/C Hit@5 변화 없음 |
| 초기 필터: 검색 문장만 과거형, 필터 고정 | Hit@5 변화 없음 |
| 초기 필터: 과거형에서 필터 재추출 | Hit@5 변화 없음 |

검색 문서의 순서나 목록이 달라지는 것과 적중률이 높아지는 것은 달랐다.
이 결과는 시제 변경이라는 한 가지 방법에 대한 단회 실험이며, 모든 리라이트가 무효하다는 뜻은 아니다.
다만 지금 리라이트를 더 확장하기보다 중복 실행을 줄이는 최적화를 선택할 근거는 된다.

### 3.3 반복 질문에서 현재 실행 비용을 줄일 수 있다

현재 요청은 조건 추출 LLM, CSV 기반 문서 준비·BM25 구성, 질문 임베딩·DB 검색,
reranker, 답변 LLM을 거칠 수 있다. 캐시를 조건 추출 앞에 두면 적중한 요청은 이 흐름을 건너뛸 수 있다.
따라서 같은 요청이 반복되는 시연이나 사용 상황에서 지연과 API 호출 감소를 기대한다.

이것은 코드 구조에서 예상한 효과다. 실제 감소 시간·비용은 측정 전이므로 수치로 주장하지 않는다.
처음 들어온 질문과 표현이 다른 질문에는 정확 일치 캐시의 이득이 없고, 조회 오버헤드는 생긴다.

### 3.4 필수 검증을 작게 구분해 설명할 수 있다

발제는 정확 일치 캐시도 허용한다. 의미 유사도 캐시, Redis, 분산 캐시를 처음부터 도입할 필요는 없다.
5문항의 첫 요청·동일 요청·버전 변경 요청을 분리하면 적중 효과와 오래된 답변 방지를 함께 보여줄 수 있다.
이는 전체 A/B/C 품질 평가를 대체하는 실험이 아니라 별도의 최적화 검증이다.

## 4. 제안하는 최소 구현

아래는 구현 시 적용할 제안이며 아직 적용된 설정이 아니다.

| 항목 | 제안 |
| --- | --- |
| 캐시 위치 | 조건 추출 전에 조회하고, 성공한 답변 생성 후 저장 |
| 저장 값 | 답변, 실제 사용한 출처 본문·메타데이터·청크 ID, 데이터 기준일, 저장 시각 |
| 질문 비교 | 입력 검증과 앞뒤 공백 제거 후 정확 일치. 숫자·문장 표현을 의미상 합치지 않음 |
| 키 | 질문 + 사용자/세션 범위 + 데이터·색인 버전 + 임베딩·생성 모델 + 조건 추출·답변 프롬프트 버전 + A/B/C·후보 수·가중치·reranker 등 검색 설정 버전 |
| 만료 | 우선 TTL 10분, 최대 100항목의 프로세스 내 메모리 캐시 |
| 무효화 | TTL 만료, 명시적 초기화, 데이터·색인·모델·프롬프트·검색 설정 버전 변경 |
| 저장 제외 | 호출 오류·timeout, 조건 확인 요청·미지원 요청, 검색 결과가 없는 응답 |
| 기록 | 요청 ID, 선택 구성, cache_hit, 캐시 버전, 전체 응답 시간, 호출 여부·상태 |
| FE 연결 | 캐시 여부와 관계없이 답변·출처·상태의 응답 형식을 동일하게 유지 |

프로세스 내 캐시는 서버 재시작 시 비워지고, 여러 서버 프로세스 간에 공유되지 않는다.
현재 최소 구현에는 이를 허용한다. 대화 이력을 나중에 추가하면 같은 질문이어도 이전 대화에 따라
의미가 달라질 수 있으므로 키에 대화 상태 버전을 포함하거나 대화 요청의 응답 캐시를 비활성화해야 한다.

기존 `execute_query`의 결과에는 LangChain Document 객체가 들어 있으므로 저장·반환 시 복사 가능한
본문·메타데이터 형태로 다룬다. 요청별 가변 목록을 공유하는 답변 체인 자체를 응답 캐시에 넣지 않는다.
데이터 갱신 시 색인 버전도 실제로 갱신해야 하며, TTL만으로 오래된 답변 문제를 해결했다고 보지 않는다.

## 5. 필수 확인 방법

답변 가능한 질문 5개를 고정하고 각 질문마다 다음 3단계를 실행해 총 15건을 남긴다.

| 단계 | 실행 | 확인 내용 |
| --- | --- | --- |
| 1 | 빈 캐시에 첫 질문 | miss, 기존 파이프라인 실행, 답변·출처 저장 |
| 2 | 같은 범위·버전·질문 재요청 | hit, 조건 추출·검색·생성 생략, 답변·출처 동일 |
| 3 | 문서/색인 버전 변경 후 같은 질문 | miss, 이전 버전 답변을 재사용하지 않고 새 처리 |

각 요청의 cache_hit, 데이터/색인 버전, 원본 답변·출처, 시간·상태를 기록한다.
버전 변경 후 응답 문장이 우연히 같아도 될 수 있으므로, 문자열 차이 대신 캐시 miss와 실제 재실행을 확인한다.
A/B/C 품질 비교에서는 캐시를 끄고 최적화 실험과 분리한다.
별도 채점 프로그램·단위 테스트 파일을 복구하지 않고도 실행 기록과 팀원 확인으로 정리할 수 있다.

## 6. 선택 결론

현재는 검색 조건과 정규화를 개선한 흐름을 유지하면서, 반복 질문의 중복 처리를 줄이는 정확 일치 캐싱을 선택한다.
필수 최적화 하나를 완료하는 것이 목적이며, 이번 단계에서 쿼리 리라이트까지 추가하지 않는다.
캐시 적중 효과와 버전 변경 후 무효화를 확인한 다음 팀의 채팅 API·FE에 연결한다.
