## 1. 이번 작업의 결과와 측정 범위

`cached_pipeline.py`에 정확 일치 응답 캐시를 구현했다. 기존 조건 추출·검색·생성 코드는 유지하고
새 호출 진입점 `CachedPipeline.answer()` 앞뒤에 캐시 조회·저장을 연결했다. 채팅 API와 FE는 작업하지 않았다.

이번에 직접 수행한 작업은 다음과 같다.

- 최초 Mac 실험의 실제 검색 ID와 개선 후 HTML의 실제 검색 ID를 같은 CSV·질문 조건으로 다시 채점했다.
- 초기 Mac, 교안 Windows 기준선, 정규화 보완 결과를 구분해 비교했다.
- 저장된 개선 후 결과를 주입해 캐시 전후 답변·출처가 유지되는지 검증했다.
- 캐시의 miss/hit/색인 버전 변경, TTL, LRU, 사용자 범위, 복사 보호, 오류 비저장을 확인했다.

**환경 제한:** 로컬 DB 연결은 `PermissionError`, OpenAI 호스트 조회는 `gaierror`로 차단됐다.
따라서 신규 검색·답변 생성·RAGAS 심사 호출과 실제 모델 포함 캐시 지연 측정은 수행하지 못했다.
아래 숫자는 저장된 실제 검색 결과에 대한 오프라인 재채점이다. 초기 문서에 있는 RAGAS 수치와
이번 조건 기반 지표는 서로 다른 방법이므로 같은 지표처럼 합치지 않는다.

## 3. 지표 정의

질문별 정답 집합 G는 원본 CSV에서 정답 조건을 **같은 거래가 전부 만족하는 청크 전체**다.
검색 집합 R은 해당 실행에서 실제 반환된 상위 최대 5개의 청크다.
관련 판정은 답변 LLM이 아닌 숫자 비교와 문자열 일치로 수행했다.
정답표는 저장 결과의 사후 채점에만 사용하며 실제 검색·캐시 키에 넣지 않는다.

| 지표 | 이번 계산 방법 | 의미 |
| --- | --- | --- |
| Hit@5 | 관련 청크가 하나 이상 있으면 1 | 최소 한 거래를 찾았는가 |
| 문서 Precision | TP / 반환 문서 수. 빈 결과는 0 | 반환된 거래 중 조건을 전부 충족하는 비율 |
| 조건판정 Context Precision(AP@5) | 각 관련 순위의 누적 Precision 합 / 상위 5개 안의 관련 수. 없으면 0 | 관련 거래가 위쪽에 있는가 |
| 집합 Recall@5 | TP / 원본의 전체 관련 거래 수 | 조건에 맞는 전체 거래 중 몇 개를 반환했는가 |
| 집합 F1@5 | 질문별 2×P×R/(P+R), 이후 17문항 평균 | 문서 Precision과 집합 Recall의 조화평균 |

TP는 R과 G의 교집합 크기다. Precision은 반환 수가 5개 미만이면 실제 반환 수를 분모로 한다.
F1은 평균 Precision·Recall로 한 번 계산하지 않고 **질문별 F1의 macro 평균**으로 계산했다.
숫자 비교는 반올림 전 메타데이터를 사용했다.

**RAGAS와의 구분:** 위 Context Precision은 RAGAS의 순위 기반 계산과 같은 형태지만
관련 여부를 ‘모든 조건 일치’라는 코드 규칙으로 판정한 별도 지표다.
RAGAS Context Recall은 참고 답안의 진술을 검색 문맥이 뒷받침하는지 보는 지표다.
이번 집합 Recall은 전체 정답 거래를 분모로 하므로 RAGAS Recall과 직접 비교할 수 없다.
예컨대 T01은 허용 거래가 1,216건이라 올바른 거래 5개를 반환해도 집합 Recall은 약 0.0041이다.
추천 사례 5개를 제시하는 목적에서 이 Recall의 낮은 값만으로 검색 실패라고 판단하면 안 된다.

## 6. 조건 추출은 어디에서 어떻게 하나

### 6.1 추출 프롬프트와 JSON 출력

`query_filters.py:15`의 `EXTRACTION_PROMPT`가 질문을 구조화하는 규칙을 정의하고,
`build_filter_extractor()`(224행)가 다음 체인을 만든다.

`질문 → ChatPromptTemplate → JSON mode LLM → StrOutputParser → parse_filter_plan`

JSON mode는 `response_format={'type': 'json_object'}`를 사용한다.
JSON 형식 출력과 조건의 의미 정확성은 다르므로 후속 검증을 수행한다.
각 조건에는 field, operator, value, source_text를 넣고, 마지막 값은 원질문에 실제 존재해야 한다.

예시 질문: ‘남현동에서 빌라 전세, 2억 5천만원 이하에 8평 이상인 집을 찾고 있어요.’

```json
{
  "conditions": [
    {"field": "region_dong", "operator": "$eq", "value": "남현동", "source_text": "남현동"},
    {"field": "housing_type", "operator": "$eq", "value": "연립다세대", "source_text": "빌라"},
    {"field": "lease_type", "operator": "$eq", "value": "전세", "source_text": "전세"},
    {"field": "deposit_manwon", "operator": "$lte", "value": 25000, "source_text": "2억 5천만원 이하"},
    {"field": "area_pyeong", "operator": "$gte", "value": 8, "source_text": "8평 이상"}
  ],
  "unsupported_conditions": [],
  "ambiguous_conditions": []
}
```

위 JSON은 설명용 예시이며 새 모델 호출 결과가 아니다.

### 6.2 검증

`parse_filter_plan()`(126행)과 `metadata_filters.validate_filter()`(16행)가 함께 검사한다.

- JSON 중복 키·NaN·Infinity, 예상하지 않은 최상위 키·필드·연산자를 거부한다.
- 조건마다 질문의 실제 부분 문자열인 source_text를 검사한다.
- 문자열은 정확 일치만, 숫자는 유한한 실수와 허용 비교 연산자만 지원한다. bool은 숫자로 받지 않는다.
- 같은 필드의 여러 조건을 임의로 덮어쓰지 않는다.
- 경계가 모호한 ‘저렴한’, ‘5평 후반대’는 확인 요청으로 보낸다.
- 관리비·주차 등 없는 속성을 검색 가능하다고 추측하지 않는다.

이 검증으로 출력 형식을 제한하지만 LLM의 잘못된 단위·의미 해석을 전부 증명하는 것은 아니다.

## 7. 정규화는 어디에서 어떻게 하나

| 대상 | 위치 | 처리 |
| --- | --- | --- |
| 금액·비교 표현 | EXTRACTION_PROMPT | 천만원→1000만원, 2억 5천만원→25000만원. 이하→$lte, 미만→$lt, 이상→$gte |
| 주택 유형 | `canonical_housing_type()`(103행), `parse_filter_plan()` | 빌라→연립다세대, 단독·다가구→단독다가구. 원룸만으로 유형 강제하지 않음 |
| 표기 | `compact_name()`(99행) | NFKC·대소문자 정리, 공백·문장부호 제거 |
| 건물명 | `resolve_building_plan()`(241행) | 지역·주택 유형 안의 원본 카탈로그에서 유일한 표기/약칭 후보만 연결 |
| 정보 요청 | `supported_information_request()`(110행) | ‘보증금 얼마인지 알려줘’를 가짜 숫자 제한으로 처리하지 않음 |
| 면적 | `parse_filter_plan()` | 정확한 ㎡와 환산상 일치하는 ‘약 몇 평’은 중복 등식 제거. 모순은 확인 요청 |

금액의 자연어 단위 해석은 별도 수학 파서가 아니라 추출 모델과 프롬프트에서 수행한다.
코드에서 직접 실행되는 주택 유형·건물명·면적 보정과 구분해야 한다.

건물명은 아파트·오피스텔 같은 유형 접미사와 공백 차이를 정리한다.
‘대창센시티 2차’처럼 약칭인 경우에도 단지·차수 번호가 같은 유일 후보만 연결한다.
후보가 여러 개거나 없으면 건물명 조건을 빼고 검색하지 않고 확인 요청을 유지한다.

면적 예시는 114.99㎡와 ‘약 34.78평’이다. 환산값을 표현 자릿수로 반올림했을 때 일치하면
정확한 ㎡ 조건만 적용한다. 모든 평수 조건을 느슨하게 반올림하는 것은 아니다.
정보 요청 판별에서도 ‘무보증’, ‘저렴한’, ‘이하’ 등 실제 제약 표현은 제거하지 않는다.

보정 내용은 `FilterPlan.normalizations`에 남고, `as_dict()`로 확인할 수 있다.

## 8. 메타데이터 필터는 어디에서 어떻게 적용하나

`structural_chunk_v0.load_and_clean()`(27행)에서 CSV의 숫자 컬럼을 숫자형으로 보존하고
`area_pyeong = area_m2 / 3.305785`를 반올림 없이 계산한다.
`create_documents()`(150행)는 지역·유형·전월세·가격·면적·출처 행 번호 등을 메타데이터로 만든다.

`execute_query()`(300행)는 검증·건물명 연결 후 처리 상태를 확인한다.
확인 요청·미지원이면 검색 전에 안내하고, 정상인 경우 `build_retrievers(search_filter=...)`로 넘긴다.

`lesson_pipeline.build_retrievers()`(93행)의 두 적용 지점이 핵심이다.

```python
local_docs = [doc for doc in documents(version)
              if matches_filter(doc.metadata, search_filter)]
filter_kwargs = {'filter': search_filter} if search_filter else {}
vector_candidates = store.as_retriever(
    search_kwargs={'k': CANDIDATES, **filter_kwargs})
keyword_retriever = BM25Retriever.from_documents(local_docs, preprocess_func=tokenize)
```

Vector는 PGVector filter로 검색 대상을 제한하고, BM25는 동일한 조건을 만족하는 문서만 색인한다.
그래서 BM25가 조건 밖 거래를 Hybrid 후보에 다시 섞는 것을 막는다.
A는 필터 적용 Vector, B는 필터 적용 Hybrid, C는 같은 Hybrid 후보를 재정렬한다.
후보가 없으면 `build_chain()`이 고정 안내를 반환하고 답변 LLM을 호출하지 않는다.

## 9. 캐싱은 어디에 붙였나

`cached_pipeline.py`의 `ResponseCache`가 TTL과 최대 항목 수를 관리한다.
`CachedPipeline.answer()`가 조건 추출 전에 키를 만들어 조회한다.

- 기본 TTL: 600초, 최대 100개, 만료 항목 제거와 LRU 교체.
- 캐시 hit: 저장된 답변·출처·추출 계획을 복사해서 반환. 조건 추출·검색·생성을 실행하지 않음.
- 캐시 miss: 기존 추출·정규화·검색·생성 호출 후 성공하고 출처가 있는 답변만 저장.
- 오류·확인 요청·미지원·근거 없음은 저장하지 않음. 오류는 호출자에게 전달.
- 키: 앞뒤 공백을 제거한 질문 + 사용자/세션 scope + 명시적 index_version + A/B/C + 코드·CSV·잠금 파일 해시.
- 모델·프롬프트·후보 수·가중치 등은 이를 정의한 실행 코드 해시로 키에 반영.
- DB 데이터가 바뀌면 호출자가 index_version을 반드시 갱신해야 함. CSV 변경만으로 DB 갱신을 대신하지 않음.
- `clear()`로 수동 초기화 가능. 사용자 간 scope를 분리하고 반환값을 deepcopy해 출처 변조가 원본 캐시에 전파되지 않게 함.

캐시 객체는 프로세스 안에서 재사용해야 한다. 요청마다 새 인스턴스를 만들면 적중하지 않는다.
현재는 단일 프로세스 메모리 캐시이고 재시작 시 비워진다. 다중 프로세스 공유·동일 동시 요청의
중복 실행 방지·대화 메모리는 구현하지 않았다. 대화 이력이 붙으면 캐시 키에도 대화 상태가 반영돼야 한다.

### 팀 대표에게 전달할 호출 예시

```python
# 기존 test/bc 모듈 경로가 import 가능하도록 설정한 뒤 사용한다.
from cached_pipeline import CachedPipeline

pipeline = CachedPipeline()  # 서비스 시작 시 생성해 재사용

result = pipeline.answer(
    '신림동에서 보증금 500만원 이하, 월세 45만원 이하인 집을 찾아줘',
    scope='session-123',
    index_version='course_v0_small:2026-11-26-v1',
    system='C',
)
# result: status, response, sources, plan, cache_hit,
# cache_key, index_version, pipeline_executed, elapsed_seconds
```

sources는 JSON으로 다루기 쉬운 id/page_content/metadata 목록이다.
기존 `execute_query()`를 직접 호출하는 경로는 계속 캐시 없는 경로다.
전체 서비스에서 캐시를 적용하려면 대표가 위 진입점을 호출해야 한다.
A/B/C 품질 비교에는 `use_cache=False`를 사용한다.

## 11. 측정 명령과 추가 측정이 필요한 항목

저장된 실제 검색 결과를 오프라인으로 다시 계산:

```sh
uv run python src/rag_home_api/test/bc/compare_saved_quality.py
```

저장된 최초·정규화 결과 각각 51건을 같은 RAGAS 심사 모델로 평가(API 과금 발생):

```sh
uv run python src/rag_home_api/test/bc/compare_saved_quality.py --ragas
```

계산 근거는 Git에서 제외한 `.local/quality_comparison.json`에 저장한다.
캐시 경계 검증 기록은 `.local/cache_validation.json`에 남겼다.
오프라인 명령은 새 질문을 모델에 질의하지 않는다. --ragas는 저장된 문맥을 심사하는 별도 API 작업이다.
실환경의 15건 캐시 측정과 새 검색·생성 평가가 필요하면 네트워크와 DB에 접근 가능한 환경에서 수행해야 한다.
이 문서는 실제로 확보한 지표와 미측정 항목을 구분한 현재 결과다.
