# 내 데이터와 평가 수치 이해하기

작성일: 2026-11-26. 현재 CSV와 저장된 실제 실행 결과를 기준으로 정리했다.

## 1. 현재 결과를 한 문장으로 설명하면

**조건 밖의 거래를 답변 근거로 가져오는 문제는 크게 줄었지만, 건물명이 다르게 표현되면 답이 있어도 검색하지 못하는 문제가 남아 있다.**

신규 질문에서 답이 있는 17개 중 15개를 찾았고, 반환한 거래 66개는 모두 질문 조건을 만족했다.
‘가져온 것은 맞다’와 ‘필요한 질문을 빠짐없이 처리했다’는 다른 평가다.

## 2. 이 CSV에는 무엇이 있나

이 데이터는 현재 판매 중인 매물 목록이 아니라 **과거에 체결된 전월세 계약 기록**이다.
같은 건물의 다른 계약이 여러 행에 있을 수 있다. 한 행을 서로 다른 현재 매물 한 개로 해석하지 않는다.

| 구분 | 실제 분포 | 서비스에서 의미하는 것 |
| --- | --- | --- |
| 전체 | 31,772거래 | 관악구 과거 거래 사례 검색용 |
| 지역 | 신림동 16,179(50.9%), 봉천동 14,398(45.3%), 남현동 1,195(3.8%) | 서울 전 지역을 대표하지 않음 |
| 전월세 | 월세 26,014(81.9%), 전세 5,758(18.1%) | 월세 거래가 다수 |
| 주택 유형 | 단독다가구 16,742, 연립다세대 5,503, 아파트 5,397, 오피스텔 4,130 | ‘원룸’이 독립된 유형 필드로 들어 있지 않음 |

| 건축연도 | 비어 있는 거래 854(2.7%) | 모든 거래에 준공연도 조건을 적용할 수 있는 것은 아님 |
| 금액·면적 | 보증금·월세·면적은 빈칸 0건 | 정형 숫자 조건 필터에 적합 |
| 건물명 종류 | 빈칸 제외 2,818종 | 이름·별칭을 관리할 원본 카탈로그가 있음 |

건물명 결측은 모두 단독다가구에서 발생했고, 층 결측도 단독다가구 거래 수와 같았다.
결측값을 LLM이 추측해서 채워서는 안 된다. 조건을 만족한다고 검증할 수 없다는 것과
실제 그 집이 존재하지 않는다는 것은 다르다.

월세 거래의 보증금 중앙값은 2,000만원, 월세 중앙값은 50만원, 면적 중앙값은 22㎡다.

이 값은 현재 CSV 전체의 과거 기록 요약이지 현재 시세·추천 예산이 아니다.

## 3. 왜 조건 추출·필터가 효과가 컸나

질문의 핵심 정보와 데이터 컬럼이 직접 연결된다.

| 사용자 표현 | 실제 필드 | 필요한 판단 |
| --- | --- | --- |
| 신림동 | region_dong | 문자열 일치 |
| 보증금 300만원 이하 | deposit_manwon | 숫자 ≤300 |
| 월세 40만원 이하 | monthly_rent_manwon | 숫자 ≤40 |
| 4평 이상 | area_pyeong | 숫자 ≥4, 반올림 전 값 |
| 빌라 | housing_type | 원본 값 연립다세대로 정규화 |

임베딩은 의미가 비슷한 거래를 찾지만 ‘이하·이상’을 수학적으로 강제하는 검색은 아니다.
필터는 조건을 만족하지 않는 거래를 후보에서 제외한다. 그래서 임베딩을 크게 바꾸는 것보다
숫자 조건을 실제 메타데이터에 연결하는 변경의 효과가 컸다.

같은 Windows 기존 Test에서 C는 기준선 10/17→초기 필터 12/17→정규화 보완 17/17이었다.
이는 조건 추출·필터·확인 요청과 정규화를 묶어 개선한 결과이며 각 요소의 독립 기여율은 측정하지 않았다.

## 4. 지금 어떤 수치가 좋고 어떤 수치가 아쉬운가

| 무엇을 보나 | 현재 확보한 결과 | 해석 |
| --- | --- | --- |
| 반환 거래가 조건을 지키는가 | 신규 결과 66/66 일치 | **좋음.** 반환한 거래에 조건 위반이 없었음 |
| 답이 있는 질문을 놓치지 않는가 | 신규 Hit@5 15/17(88.2%) | **개선 여지 있음.** 2개 질문은 답이 있어도 검색을 진행하지 못함 |
| 기존 문맥이 참고 정답을 뒷받침하는가 | 기존 C의 RAGAS Recall 1.0000 | **기존 질문에서는 좋음.** 새 질문 Recall을 측정한 값은 아님 |
| 관련 문맥이 위쪽에 있는가 | 기존 A/B/C의 RAGAS Precision 약 1.0 | 조건 필터 뒤 높은 점수. 일반 챗봇 정확도 100%를 뜻하지 않음 |
| 모든 정답 거래를 몇 개 회수하는가 | 기존 집합 Recall@5 0.2481 | 최대 5개만 반환하는 구조라 낮을 수 있음. 사례 추천에서 이것만 보고 나쁘다고 판단하지 않음 |
| 답변 문장·금액·인용까지 맞는가 | 최신 구성의 전체 정답·인용 검토 미완료 | **아직 평가 부족.** 검색 지표로 대신 말할 수 없음 |
| 같은 질문이 빨라지는가 | 캐시 기능 검증만 완료 | 실제 지연·비용 개선 수치는 **미측정** |

반환 거래의 66/66은 문서 단위 집계다. 검색하지 못한 2문항에는 반환 문서가 없으므로 이 비율에 포함되지 않는다.
따라서 문서 Precision 100%와 질문 Hit@5 88.2%가 동시에 나오는 것은 모순이 아니다.

### ‘재현율이 높다’는 말도 어떤 재현율인지 구분해야 한다

- **Hit@5:** 조건에 맞는 사례가 하나라도 나왔는지 본다. 사례 검색 목적에 직접적이다.
- **RAGAS Context Recall:** 참고 정답의 진술이 문맥으로 뒷받침되는지 LLM이 심사한다.
- **집합 Recall@5:** 조건에 맞는 원본 거래 전체 중 몇 개를 반환했는지 본다.

예를 들어 T01에 조건 일치 거래가 1,216건 있다. 맞는 거래 5개를 반환하면
Hit@5는 1, 문서 Precision은 1, 집합 Recall은 5/1,216≈0.0041이다.
‘사례를 5개 보여주기’는 성공했지만 ‘전체 거래를 다 회수하기’는 하지 않은 것이다.
통계가 목적이면 이 상위 5개를 쓰지 말고 전체 필터 결과를 SQL로 집계해야 한다.

## 5. 앞으로 개선할 대상은 무엇인가

### 우선 1: 어떤 종류의 실패인지 나눠 보기

| 실패 종류 | 실제 사례·데이터 한계 | 맞는 개선 방향 |
| --- | --- | --- |
| 이름 표현 차이 | T31 관악 현대↔현대(관악), T33 한글↔영문 | 건물명 카탈로그·명시적 별칭과 유일 후보 확인 |
| 모호한 조건 | D08 ‘5평 후반대’ | 사용자가 원하는 범위를 질문하기 |
| 데이터에 값이 없음 | 단독다가구 층·건물명 결측 | 값이 없는 이유와 확인 한계를 안내. 추측하지 않기 |
| 속성 자체가 없음 | 관리비·주차·옵션 | 추가 데이터 확보 또는 미지원 안내 |
| 문맥은 맞는데 답변이 틀림 | 최신 전체 판정 미완료 | 원본 문맥과 답변·인용을 대조하고 생성 단계 개선 |
| 응답이 느림 | 신규 C 20문항 평균 6.724초, 첫 요청 28.049초 | 모델 로딩·문서 준비·검색·생성 시간을 나눠 측정 |

지금 실제 신규 미적중 2건은 이름 연결 문제다. 따라서 다음 검색 개선 후보는
임베딩 모델 확대보다 **원본 건물명과 사용자 별칭을 연결하는 방식**이다.
다만 T31·T33을 보고 수정하면 이후 결과는 신규 최종 점수가 아니라 후속 개선 실험으로 기록해야 한다.

### 우선 2: 고정한 별칭·단위 경계 사례로 점검

다음은 아직 실행하지 않은 후속 검증 설계다.

- 원본 이름, 공백 차이, 유형 접미사, 단어 순서, 한글/영문, 비슷하지만 다른 단지명을 구분한다.
- 건물명이 없거나 후보가 여러 개인 경우는 자동 연결하지 않는 기준도 함께 정한다.
- 금액 단위·이하/미만·면적 환산·결측 층의 처리도 분리해 확인한다.
- 하나의 전체 점수 외에 유형별 적중·확인 요청·잘못 연결한 건수를 같이 본다.

### 우선 3: 반환 답변의 품질과 캐시의 실제 이득 확인

최신 답변이 계약일·금액·단위를 맞게 설명하고 실제 검색 ID를 인용하는지 원문과 비교한다.
캐시는 별도로 같은 질문의 miss/hit/버전 변경을 실행해 시간과 호출 사용량을 기록한다.
검색 품질이 좋아진 것과 반복 질문이 빨라진 것을 같은 성과로 합치지 않는다.

## 6. 선택한 이유를 판단하는 기준

| 선택 | 현재 선택한 이유 | 아직 증명하지 않은 것 |
| --- | --- | --- |
| 거래당 1청크 | 지역·금액·면적을 같은 거래 안에서 판단하고 출처 행과 연결하기 쉬움 | 다른 모든 청킹보다 항상 우수함 |
| V0/small | Dev Hit@5·MRR·당시 비용 비교에서 선택 기준 충족 | large·요약이 모든 질문에서 불필요함 |
| 조건 추출·공통 필터 | 정형 데이터의 숫자·지역 조건을 두 검색 경로에서 강제 | 모호한 표현·잘못 추출된 조건을 모두 해결함 |
| 정규화 | 원본 표기와 질문 표현 차이로 인한 누락 감소 | 모든 별칭·한영 표기·순서 변형을 처리함 |
| 기본 C | 초기·교안 기준선에서 B보다 적중 수가 높았고 비교 구성을 유지 | 필터 보완 후에도 C가 A/B보다 실서비스에서 최적임 |
| 정확 일치 캐시 | 검색 의미를 추가로 바꾸지 않고 반복 요청을 줄이는 필수 최적화 | 실제 서비스에서 충분한 반복률·시간·비용 이득이 있음 |

정규화 후 기존 A/B/C는 모두 17/17이었다. 이 단계의 품질 수치만으로 C가 반드시 필요하다고 결론낼 수 없다.
실제 선택에는 새 질문에서의 차이와 재정렬 지연을 함께 봐야 하며, 지금 신규 질문은 C만 실행했다.
