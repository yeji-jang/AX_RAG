# Context Precision 1.0의 의미와 추가 검증

작성일: 2026-11-26

> 후속 검증: 미사용 T21~T40의 C 구성 검색·생성 20건이 실행됐고,
> 채점 ID 오류 수정 후 저장 결과 재채점에서 Hit@5는 15/17(88.2%)이었다.
> [실환경·미사용 질문 분석](./runtime_measurement_analysis.md)에 결과와 미적중 원인을 정리했다.
> 아래 추가 측정 준비 설명은 그 이전 시점의 이력이다.

## 결론

**1.0이라는 값 자체를 오류라고 볼 수는 없다. 다만 현재 수치를 일반적인 챗봇 정확도로 해석하면 안 된다.**
이번 값은 이미 분석한 기존 17문항에서 조건 필터·정규화를 거친 검색 문맥에 대한 평가다.
검색 조건을 모두 만족하는 거래만 후보로 남기므로 이 범위에서 높은 값이 나올 수 있다.

## 실제로 대조한 내용

| 점검 | 결과 |
| --- | --- |
| 개선 후 A/B/C, 근거 있는 17문항의 반환 문맥 | 총 252개 |
| 원본 CSV에서 모든 정답 조건을 만족하는 반환 거래 | 252/252 |
| 저장 문맥이 해당 청크의 실제 원문 본문과 일치 | 252/252 |
| 원본에 없는 청크 ID | 0개 |
| RAGAS 결과 6개 묶음 | 입력 102개, 원본 점수와 평균 대조 완료 |

같은 거래가 A/B/C에서 반복될 수 있으므로 252는 고유 거래 수가 아니라 반환 문맥의 합계다.
각 문맥이 실제 원문과 연결되는지, 질문 조건을 만족하는지는 LLM 평가와 별도로 확인했다.
현재 검색 코드의 입력은 질문과 추출 필터이며, 비교 스크립트의 정답표는 검색 후 채점·심사에 사용한다.
이 점검에서 직접적인 정답표 유입 증거는 확인하지 못했다. 모든 실행 이력의 무결성을 보증한다는 뜻은 아니다.

## Context Precision은 문서 정밀도와 다르다

설치된 RAGAS의 `LLMContextPrecisionWithReference`는 문맥마다 관련 여부를 판정한 뒤
각 관련 문맥 순위의 누적 Precision을 평균한다. 분모는 반환 결과 안의 관련 문맥 수다.

예를 들어 판정이 `[1, 0, 0, 0, 0]`이면 Context Precision은 거의 1.0이지만,
반환 문서 중 관련 문서 비율은 1/5 = 0.2다. 따라서 Context Precision 하나만 보면 안 된다.
이번에는 독립적으로 검사한 문서 Precision도 252/252라 높은 값에 근거가 있다.

실제 저장된 RAGAS 값은 부동소수점 보정으로 약 0.99999999998이며 표에서 1.0000으로 반올림했다.
임의로 1.0을 대입한 결과는 아니다.

## 점수가 높아지기 쉬운 평가 범위

1. 질문의 핵심이 데이터에 명시된 지역·유형·가격·면적 등 정형 조건이다.
2. 같은 조건을 검색 필터와 사후 정답 기준에서 검사하므로 정확히 추출했을 때 적합 문맥만 남기기 쉽다.
3. 참고 정답이 특정 거래 하나가 아닌 ‘조건을 만족하는 거래의 존재’ 중심이다. 다양한 적합 거래를 정답으로 허용한다.
4. 기존 Test를 분석하며 공통 정규화 규칙을 수정했다. 독립적인 최종 평가로 볼 수 없다.
5. 출처 문맥의 관련성을 보는 값이며 실제 답변의 오류·정보 부족 대응·새 표현 처리 능력을 모두 측정하지 않는다.

이 구조는 조건 기반 거래 검색 목적에는 타당하지만, 복잡한 공고문 종합·법령 예외 판단까지 잘한다고 확장할 근거는 아니다.
조건 추출이 틀리거나 애매한 새 질문에서는 검색 실패·조건 위반이 발생할 수 있다.

## T16: 데이터 부족보다는 평가 민감도를 먼저 의심할 근거

| 항목 | 실제 확인 |
| --- | --- |
| A/B/C의 질문 | 동일 |
| A/B/C의 참고 정답 | 동일 |
| A/B/C의 반환 거래 집합 | 같은 5개 거래 |
| 거래 순서 | 다름 |
| 조건 검사 | 세 구성 모두 반환 거래 5개가 전부 조건 충족 |
| RAGAS Recall | A 0.6667, B/C 1.0000 |

따라서 A가 필수 거래를 덜 검색했다고 단정할 수 없다. LLM 심사 변동·문맥 순서 민감도·참고 정답의
진술 분해 차이가 후보 원인이다. 현재 점수 체크포인트에는 판정 이유가 없어 어느 원인인지 확정하지 않았다.
참고 정답에는 ‘보증금을 원문대로 안내한다’ 같은 응답 지침도 들어 있어, 사실 진술을 전제로 하는
Recall 심사에서 지침을 어떻게 해석하는지도 별도로 확인할 필요가 있다.
높은 점수를 얻기 위해 지금 참고 정답을 바꾸고 기존 결과와 섞어 비교하지 않는다.

## 추가 측정 준비

`measure_runtime.py`는 실제 모델·DB를 사용하는 별도 측정기다.
현재 문서 작성 환경에서는 외부 API·DB 접근이 차단돼 다음 작업은 아직 실행하지 않았다.

| 항목 | 실행 범위 | 기록 |
| --- | --- | --- |
| 캐시 실환경 | 5문항 × 최초·동일 질문 적중·버전 변경 = 15건 | 원본 답변·출처·시간·LLM 토큰 사용량 |
| 미사용 질문 | 기존 v3 초안 T21~T40, C 구성, 캐시 끔 | 질문·코드·데이터 버전 고정, Hit@5, 원본 답변·출처·오류 |
| T16 심사 대조 | A/B/C 원래 순서와 고정 순서를 각각 3회 심사, 총 12회 | 진술별 판정 이유·Recall·반복 편차 |

새 폴더를 지정해 실행한다. API 비용과 모델 다운로드가 발생할 수 있다.

```sh
uv run python src/rag_home_api/test/bc/measure_runtime.py --stage all --output src/rag_home_api/test/bc/.local/runtime_measurement_20261126
```

완료한 항목의 실제 수치만 `docs/runtime_measurement_analysis.md`로 작성한다.
캐시 시간 측정과 새 질문 검색은 기존 RAGAS 재채점과 다르다.
LLM 사용량은 조건 추출·답변 모델 기준이며 임베딩 토큰·실제 청구 금액까지 포함한 비용 측정은 아니다.
새 질문 결과는 근거 없는 문항의 안내와 답변 의미 정확도를 원본 기록으로 교차 검토해야 한다.
이 측정기는 그 수동 검토를 자동으로 통과 처리하지 않는다.

T16의 반복 심사는 기존 점수를 캐시해 재사용하지 않는다. 반복 3회는 원인을 탐색하기 위한 소규모 대조이며
순서의 인과 효과나 통계적 유의성을 확정하지 않는다. 현재는 동일 집합·다른 순서라는 증거만 확보했다.

## 발표에서 사용할 수 있는 표현

‘기존에 분석한 17문항에서 조건 추출·필터·정규화를 적용한 저장 검색 결과의 Context Precision은
A/B/C 모두 약 1.0이었다. 별도로 원본 조건을 검사했을 때 반환 문맥 252개가 모두 적합했다.
이는 기존 조건 검색의 개선 결과이며, 새 질문과 답변 정확도·캐시 지연은 별도 검증 대상이다.’
