> 추가 상세 분석과 측정 도구는 개인 로컬 자료이며, 아래 집계만으로 개선 과정과 한계를 확인할 수 있음.

- 공유 범위: 전월세 CSV의 구조 청킹·임베딩 비교, A/B/C 검색, 조건 추출·필터·정규화, 캐싱, 기존·신규 질문 평가.
- 실패하거나 수치가 오르지 않은 시도도 남김. 기존 질문을 보고 보완한 결과와 신규 질문 결과를 구분함.
- 청킹 V0/V1과 필터 개선 v1/v2는 다른 구분임. 필터를 바꿀 때 청킹은 V0를 유지함.
- 과거 실거래를 근거로 참고 사례를 안내하는 평가임. 현재 매물 존재·입주 가능 여부·현재 호가는 확인하지 못함.

### 1-1. 결과가 다음 선택으로 이어진 과정

아래 표의 선택은 실제로 채택한 것과 후속 개선 후보를 구분함. 새로운 실험을 수행한 표가 아님.

| 순서·시도 | 확인한 결과 | 결과를 어떻게 해석했나 | 선택한 것 | 다음에 확인할 문제 |
| --- | --- | --- | --- | --- |
| 1. 거래 데이터를 청크로 구성 | 한 거래 안에 지역·유형·금액·면적이 함께 있음 | 여러 거래의 조건을 섞으면 존재하지 않는 정답을 만들 수 있음 | 거래당 1청크, 숫자 메타데이터와 원본 행 연결 | 요약 추가·임베딩 확대가 검색에 유리한가 |
| 2. V0/V1×small/large 비교 | V0/small과 V1/large는 Dev 3/8로 같고 MRR은 0.375 대 0.208 | 큰 모델·요약 추가의 이득이 확인되지 않았고 V0/small이 선택 기준 충족 | V0/small 유지 | 본문보다 검색 방식이 병목인가 |
| 3. 초기 A/B/C 비교 | 기존 Test A 6/17, B 5/17, C 8/17 | Hybrid가 오히려 악화될 수 있고, 재정렬도 후보 누락을 해결하지 못함 | A/B/C 비교를 유지하고 교안 구성으로 연결 | 후보 단계에서 어떤 조건을 어기는가 |
| 4. 교안 기준선 확인 | Windows A 6/17, B 7/17, C 10/17 | C가 가장 많이 맞혔지만 기존 17문항 중 7개는 여전히 실패 | C 기본값 유지, 모델 확대보다 조건 처리 우선 | 숫자·지역 조건을 검색 전에 강제할 수 있는가 |
| 5. 조건 추출·공통 필터 | 기존 Test A/B/C 각각 12/17 | 조건을 만족하지 않는 후보를 줄였지만 이름·정보 요청 해석 문제는 남음 | Vector·BM25 모두 필터 적용 | 필터가 정답을 막는 표현 차이는 무엇인가 |
| 6. 현재형/과거형 비교 | 필터 없음·고정·재추출 비교에서 Hit@5 변화 없음 | 시제만 바꾸는 시도에서는 검색 이득이 없음 | 시제 변환을 기본 검색에 넣지 않음 | 명칭·면적·정보 요청 구분을 보완 |
| 7. 정규화 보완 | 기존 Test 12/17→17/17, Dev 6/8→7/8 | 기존 실패 5문항은 표기·조건 해석 보완으로 회복. 모호한 D08은 남음 | 공통 정규화 규칙 채택, 모호한 범위는 확인 요청 | 이미 본 질문 밖에서도 같은 효과가 있는가 |
| 8. 최적화 방식 선택 | 조건 검색은 개선됐고 시제 변경의 이득은 없음. 반복 요청은 같은 처리 경로를 다시 실행함 | 추가 질의 변환보다 현재 검색을 유지하며 반복 연산을 줄이는 편이 범위가 명확함 | 필수 최적화로 정확 일치 캐시 구현 | 실제 반복 요청에서 시간·호출이 얼마나 줄어드는가 — 아직 미측정 |
| 9. RAGAS 재평가 | 기존 C Precision 0.4706→1.0000, Recall 0.4559→1.0000 | 기존 질문 문맥의 관련성·정답 지원도는 상승. 서비스 전체 정확도와는 다름 | 기존 결과의 개선 근거로 기록 | 고득점이 새로운 표현에서도 유지되는가 |
| 10. 신규 T21~T40 실행 | Hit@5 15/17, 반환 거래 66/66 조건 충족. T31/T33은 이름 연결 실패 | 가져온 거래는 맞지만 다른 이름 표현 때문에 검색을 시작하지 못한 질문이 있음 | 현 결과를 고정·보존. 아직 검색 규칙은 바꾸지 않음 | 후속 후보는 건물명 별칭·한영 표기·순서 연결이며, 보완 시 새 실험으로 구분 |

**현재 도달점:** V0/small과 조건 추출·필터·정규화, 캐시를 구현했고 신규 질문으로 이름 연결 한계를 확인함.
이후 후보인 별칭 보완·실환경 캐시 측정·최신 답변 품질 검토를 이미 완료한 작업처럼 적지 않음.

## 2. 데이터·청크 [팀 공유]

### 2-1. 범위

| 항목 | 값 |
| --- | --- |
| 입력 | `shared/docs/서울_전월세_최근1년_관악구.csv` |
| 원본 거래 | 31,772건 |
| 계약일 | 2025-11-24~2026-11-20 |
| 거래 유형 | 전세·월세 |
| 주택 유형 | 아파트·오피스텔·연립다세대·단독다가구 |
| 숫자 단위 | 보증금·월세는 만원, 임대면적은 ㎡. 평수는 ㎡/3.305785 |
| 출처 연결 | 거래 ID·청크 ID·원본 CSV 행 번호 |

이 데이터는 현재 입주 가능한 매물 목록이 아니라 과거 계약 기록임.
신림동 50.9%·봉천동 45.3%·남현동 3.8%, 월세 81.9%·전세 18.1%임.
건물명은 52.6%, 층은 52.7%가 비어 있어 모든 거래에서 건물·층 조건을 확인할 수는 없음.
반면 보증금·월세·면적의 빈칸은 0건이어서 정형 숫자 필터를 적용할 기반은 있음.
없는 데이터는 임베딩 확대·정규화·캐싱으로 만들어낼 수 없음.

### 2-2. 전처리·메타데이터

- `structural_chunk_v0.load_and_clean()`에서 앞뒤 공백·결측값을 정리하고 금액·면적·층·건축연도를 숫자로 유지함.
- 평수는 반올림 전 값으로 비교함. 본문에 보이는 약 평수만 소수 둘째 자리로 표시함.
- `create_documents()`에서 지역·건물·유형·전월세·금액·면적·계약일·원본 행을 메타데이터로 넣음.
- 거래 한 건의 조건이 흩어지지 않도록 거래당 1청크로 만듦. 이 데이터의 구조 청킹은 고정 글자 수 분할과 다름.
- 결측 항목은 본문에서 생략하되 실제 0은 남김. 면적을 전용·공급면적으로 바꾸어 해석하지 않음.

### 2-3. 같은 거래의 V0/V1 본문 비교

- 대상: 거래 `SR_22853de57dd8`, 원본 CSV 15,648행. 현재 청킹 코드로 같은 원본 행을 재구성한 예시임.
- 원본 행의 숫자와 상세 정보는 같고, V1에서 앞쪽 검색용 요약이 추가되는 차이를 확인함.

**V0 — 상세 본문**

```text
자치구: 관악구
법정동: 신림동

주택 유형: 단독다가구
임대면적: 17㎡ (약 5.14평)
건축연도: 1997년

전월세 구분: 월세
계약일: 2026-04-24
계약기간: 2026-05~2027-05
계약구분: 신규

보증금: 300만원
월세: 40만원
```

**V1 — 추가되는 요약**

```text
관악구 신림동 단독다가구 월세, 임대면적 17㎡ (약 5.14평) 거래 사례. 보증금 300만원, 월세 40만원.
```

- V1의 최종 본문은 위 요약 + 빈 줄 + V0와 같은 상세 본문임.
- 거래마다 요약이 늘어 전체 입력 토큰은 5,168,969→7,380,407로 늘었지만 Dev 적중률은 뚜렷하게 오르지 않음.
- 이 예시는 본문 차이를 보여주는 것이며 이 문서 보강 과정에서 재임베딩하거나 새 검색을 수행하지 않음.

## 3. 청킹·임베딩 비교 [개인 / 팀 비교 자료]

### 3-1. 바꾼 것

- V0: 상세 본문만 사용함. `structural_chunk_v0.py`.
- V1: 같은 상세 본문에 지역·주택·가격의 검색용 요약을 추가함. `structural_chunk_v1.add_search_columns()`.
- 각 본문에 small(1,536차원)·large(3,072차원)를 적용해 네 조합을 비교함.
- 같은 CSV·Dev 질문, exact cosine 검색으로 비교함. 이 단계에서는 BM25·reranker·조건 필터를 넣지 않음.

### 3-2. 결과

| 조합 | Dev Hit@5 | MRR@5 | 본문 입력 토큰 | 당시 1회 임베딩 추정 비용 |
| --- | ---: | ---: | ---: | ---: |
| V0/small | 3/8 (37.5%) | 0.375 | 5,168,969 | $0.1034 |
| V0/large | 2/8 (25.0%) | 0.250 | 5,168,969 | $0.6720 |
| V1/small | 2/8 (25.0%) | 0.150 | 7,380,407 | $0.1476 |
| V1/large | 3/8 (37.5%) | 0.208 | 7,380,407 | $0.9595 |

- 선택: **V0/small**. Hit@5→MRR→비용 순서로 봄. V1/large와 적중 수는 같지만 MRR·비용에서 V0/small이 나았음.
- 요약을 붙이거나 모델을 키우는 것만으로 조건 검색 문제가 해결되지 않음.
- Dev 답 있음은 8개뿐임. 한 문항 차이가 12.5%p라 일반적인 우열로 단정하지 않음.
- 비용은 당시 보고서 추정치임. 현재 가격표나 실제 청구 금액이 아님.
- 상세: 개인 상세자료 `docs/embedding_comparison_report.md`(청킹·임베딩 비교).

### 3-4. 왜 거래당 1청크와 V0/small을 선택했나

- 비교 단위가 집의 소개 문단이 아니라 계약 한 건임. 가격은 A거래, 면적은 B거래에서 가져오면 조건을 잘못 만족시킬 수 있어 한 거래의 속성을 묶음.
- 숫자는 본문뿐 아니라 메타데이터에도 유지해야 ‘이하/이상’ 조건을 강제할 수 있음. 청킹을 잘게 나누는 것보다 거래 식별성과 숫자형 보존이 우선이었음.
- V1은 상세 본문을 버린 것이 아니라 요약을 추가한 대안임. 실제 비교에서는 토큰이 늘어도 Hit@5 개선이 뚜렷하지 않았음.
- V0/small과 V1/large는 Dev 3/8로 같았지만 MRR은 0.375 대 0.208이고 당시 추정 비용은 $0.1034 대 $0.9595였음. 선택 기준에 따라 V0/small을 고름.
- 임베딩을 크게 만드는 대신 조건 처리에 집중한 것은 임베딩 표현력보다 숫자 비교·명칭 연결이 실제 실패 원인으로 확인됐기 때문임.

### 6-4. 왜 전체 후보 확대나 재정렬만으로 해결하지 않았나

- 상위 후보를 늘리면 정답이 포함될 가능성은 높아지지만 보증금·면적·지역 위반을 반드시 제거하지는 못함.
- reranker는 이미 들어온 후보를 비교하는 단계임. 후보에 없는 정답을 만들어 넣을 수 없음.
- 현재 CSV는 보증금·월세·면적의 결측이 0건이라 이런 조건을 직접 비교할 수 있음. 숫자 조건을 텍스트 유사도로만 판단할 이유가 적었음.
- 그래서 조건 추출로 질문을 필드에 연결하고, Vector·BM25 양쪽에서 조건을 강제한 뒤 남은 문맥을 검색·재정렬함.
- 필터가 틀리면 정답 후보도 제거될 수 있어 원문 인용 검증·모호한 조건 확인 요청을 함께 둠. 필터가 항상 옳다는 전제는 아님.

### 9-3. 왜 쿼리 리라이팅 대신 캐싱을 선택했나

| 판단 기준 | 현재 확인한 근거 | 선택에 미친 영향 |

| 해소한 병목 | 공통 필터·정규화로 기존 C 10/17→12/17→17/17 | 같은 검색 흐름을 유지하며 다른 비용을 줄이는 최적화를 선택 |

| 구현 범위 | 키·TTL·무효화를 정의한 정확 일치 캐시로 시작 가능 | 필수 최적화 하나를 추가하고 팀 통합에 연결하기에 범위가 명확함 |

## 10. RAGAS·검색 지표 비교 [팀 공유]

### 10-1. RAGAS Context Precision·Recall

- 저장된 최초 Mac·정규화 보완 문맥을 같은 심사 설정으로 재평가함. 각 17문항×A/B/C, 총 102개 입력임.
- 새 질문 검색을 다시 실행한 것은 아님. 아래 초기 값은 이번 재채점 값이며 과거 보고서 평균과 섞지 않음.
- 최초와 현재는 BM25·reranker도 다르므로 전체 변화가 필터 하나의 효과라고 단정하지 않음.

| 구성 | 초기 Precision | 개선 Precision | 차이 | 초기 Recall | 개선 Recall | 차이 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| A | 0.2718 | 1.0000 | +0.7282 | 0.3235 | 0.9804 | +0.6569 |
| B | 0.1554 | 1.0000 | +0.8446 | 0.3361 | 1.0000 | +0.6639 |
| C | 0.4706 | 1.0000 | +0.5294 | 0.4559 | 1.0000 | +0.5441 |

- Context Precision은 관련 문맥이 위쪽에 있는지를 봄. 관련 문맥이 첫 번째 하나뿐이어도 높은 값이 나올 수 있어 문서 적합 비율과 함께 확인함.
- 개선 후 반환 문맥 252개를 원본과 대조함. 252개 모두 본문이 원본과 일치하고 정답 조건을 만족함. 고유 거래 252개라는 뜻은 아님.
- T16은 A/B/C가 같은 거래 5개를 다른 순서로 찾았는데 Recall만 A 0.6667, B/C 1.0임. 데이터 누락으로 단정하지 않음.
- 같은 순서 반복·순서 변경 심사는 실행기를 준비했으나 실제 측정 결과는 아직 없음.
- 기존 질문을 보고 보완한 결과임. Context Precision 1.0을 챗봇 정확도 100%라고 표현하지 않음.

### 10-2. 조건 일치 기준 Precision·Recall·F1

- 원본 CSV에서 모든 조건을 만족하는 거래 전체를 정답 집합으로 두고 사후 계산함.
- 문서 Precision = 맞는 반환 거래/반환 거래. 집합 Recall = 맞는 반환 거래/전체 정답 거래.
- F1은 질문별 Precision·Recall의 조화평균을 구한 뒤 평균함. RAGAS Recall과 다른 지표임.

| 구성 | 초기 문서 Precision | 개선 | 초기 집합 Recall@5 | 개선 | 초기 집합 F1@5 | 개선 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| A | 0.2353 | 1.0000 | 0.0832 | 0.2481 | 0.0948 | 0.3370 |
| B | 0.1412 | 1.0000 | 0.0576 | 0.2481 | 0.0627 | 0.3370 |
| C | 0.3059 | 1.0000 | 0.0926 | 0.2481 | 0.1113 | 0.3370 |

- 관련 거래가 수백 건이어도 최대 5개만 반환하므로 집합 Recall은 낮을 수 있음.
- 이번 재평가에서 Faithfulness·Answer Relevancy를 새로 측정하지는 않음.
- 원본 수치·질문별 값: 개인 상세자료 `docs/ragas_comparison_analysis.md`(RAGAS 실측). 해석: 개인 상세자료 `docs/context_precision_audit.md`(Precision 점검).

| 질문 | 수치·근거 | 현재 판단 |

### 12-0. 팀 서비스에서 호출하는 방법과 인계 변경

이번 정리는 팀 코드와 함께 import할 때의 모듈 충돌을 줄이는 변경임. 검색 프롬프트·정규화 규칙·A/B/C 후보 수·모델은 바꾸지 않았고, 위 실험 수치를 새로 측정한 것으로 취급하지 않음.

| 위치 | 변경 | 목적 |
| --- | --- | --- |
| `__init__.py` | `CachedPipeline`, `ResponseCache` 공개 진입점 | 팀 코드가 내부 파일 경로를 조작하지 않고 import |
| `lesson_pipeline.py`, `query_filters.py`, `cached_pipeline.py`, `run_course_index.py` | 패키지 상대 import, 기존 파일 직접 실행은 유지 | 다른 팀의 같은 이름 모듈과 충돌 방지, 전역 sys.path 변경 제거 |
| `lesson_pipeline.py` | Hugging Face 관련 환경변수는 설정되지 않은 경우만 기본값 지정 | 팀이 지정한 모델 캐시·런타임 설정 존중 |
| `cached_pipeline.py` | 출처 `id`는 원본 `metadata.chunk_id` 우선, `storage_id`는 DB Document.id | DB 컬렉션 접두어와 청크 인용 ID를 구분 |
| `requirements-reranker.txt` | 현재 Mac의 추가 모델 의존성 기록 | 루트 의존성 파일을 변경하지 않고 필요한 환경 전달 |

저장소의 프로젝트 환경을 설치하고 `src`가 Python 모듈 경로에 있어야 함. 루트 의존성은 `uv sync --locked` 기준이며 C의 reranker는 별도 의존성·모델 캐시가 필요함. 현재 구현은 A/B/C 검색기를 함께 구성하므로 A/B를 선택해도 검색기 생성 시 reranker가 준비되어야 함. 추가 패키지 버전은 Mac 실행 환경 값이며 Windows의 CPU torch 호환성까지 보증하는 값은 아님.

```python
from rag_home_api.test.bc import CachedPipeline, ResponseCache

# 서버 프로세스 시작 시 생성하고 재사용. 이 생성만으로 모델·DB 호출은 하지 않음.
pipeline = CachedPipeline(cache=ResponseCache(ttl_seconds=600, max_entries=100))

# HTTP 인증/세션과 아래 값 연결은 팀 서비스 담당자가 수행.
result = pipeline.answer(
    '신림동에서 보증금 500만원 이하, 월세 45만원 이하인 집을 찾아줘',
    scope='server-managed-session-id',
    index_version='course_v0_small:2026-11-26-v1',
    system='C',
)
```

| 반환 필드 | 의미 |
| --- | --- |
| `status` | `success`, `needs_clarification`, `unsupported`. `success`라도 근거가 0건일 수 있음 |
| `response` | 과거 거래 범위를 밝힌 답변 또는 안내 |
| `sources` | 실제 사용한 근거. `id`, `storage_id`, `page_content`, `metadata` |
| `plan` | 필터·추출 조건·미지원/모호한 조건·정규화 내역 |
| `cache_hit`, `pipeline_executed` | 응답 재사용 여부와 파이프라인 실행 여부 |
| `elapsed_seconds` | 이번 호출 처리 시간. 비용 측정이나 품질 점수가 아님 |
| `index_version`, `cache_key` | 요청에 적용한 색인 버전과 캐시 키 |

- 루트 환경변수/`.env`: `OPENAI_API_KEY`, `DATABASE_URL`. 코드의 임베딩은 `text-embedding-3-small`, 생성은 `gpt-6-luna`로 고정되어 있음. `LLM_MODEL`·`EMBEDDING_MODEL` 환경변수가 이 모듈의 고정 모델을 자동 변경하지 않음.
- DB는 PGVector `course_v0_small` 컬렉션을 사용하며 법령 `jh_1000`·공공임대 컬렉션과 구분함. `pre_delete_collection=False`이고 다른 컬렉션을 삭제하지 않음.
- 저장된 원본 청크·본문·메타데이터가 같은 행만 임베딩을 재사용함. DB 갱신 시 팀 서비스가 `index_version`을 변경해야 함.
- 비용 없는 청킹 확인: `python -m rag_home_api.test.bc.run_course_index --stage check`. 이 명령은 API·DB 연결·reranker 초기화를 수행하지 않음.
- 실제 임베딩/DB 적재: `python -m rag_home_api.test.bc.run_course_index --stage index`. 기존 동일 실행 기록을 재개할 때만 `--resume` 사용. 이 단계는 API 호출과 DB 쓰기를 수행함.
- 캐시는 TTL 600초·100항목의 프로세스별 메모리 캐시이며, 정상 답변과 실제 근거가 있을 때만 저장함. TTL 만료·LRU·scope 분리·색인 버전 변경·코드/CSV/lock 변경을 반영함.
- 대화 이력은 아직 입력/캐시 키에 없음. 팀이 대화 맥락을 추가하면 키에도 포함해야 하며, 세션 범위는 서버가 관리해야 함. 다중 worker 간 캐시는 공유하지 않고 동시 동일 요청을 하나로 합치는 기능도 없음.
- HTTP 채팅 API·FE·법령/공공임대 라우팅은 팀 대표 담당이며 이 모듈에 구현하지 않음.

## 13. 남은 한계 [팀 공유]

- 데이터는 과거 거래임. 현재 매물 존재·입주 가능 여부·호가를 검증하지 못함.
- 기존 Test 17/17과 RAGAS 고득점은 이미 분석한 질문의 회귀 평가임. 신규 질문에서는 건물명 표현 차이로 2문항을 놓침.
- 현재 건물명 정규화는 공백·유형 접미사·유일한 번호 약칭 중심임. 한글/영문·단어 순서·다중 후보 처리는 한계가 남음.
- 모호한 범위나 현재 스키마가 지원하지 않는 복합 조건은 확인 요청·미지원 안내가 될 수 있음.
- 캐시의 실제 응답 시간·토큰·청구 비용 절감과 T16 심사 반복 편차는 아직 실측 결과가 없음.
- 최신 개선 구성의 전체 답변 정답률·인용 적합률과 Faithfulness·Answer Relevancy는 별도 완료 점수가 없음. 초기 자동 판정 점수로 대체하지 않음.
- 검색 적중·문맥 품질과 실제 답변의 핵심 사실·인용 정확도는 다른 문제임. 팀 통합 뒤 원문·답변 교차 검토가 필요함.
- 위 기록은 일반 전월세 개인 파트임. 공공임대·법령을 합친 서비스 전체의 정확도를 측정한 결과는 아님.
