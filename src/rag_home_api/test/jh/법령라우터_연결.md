# 개인 법령 경로와 팀 서비스 연결 위치

## 확인한 상태

- origin/dev 1f38b5ed785e5a5f534ac4169ee2931f7d7ec537에는 공용 질문 API·서비스 라우터가 없음. 공통 설정·벡터 저장소 뼈대와 데이터가 있음.
- origin/feat/kihyeok ba02ec570bdacbd449c421270e01707c17f67aef에는 retrieval/search_hybrid_rrf 계열이 개발 중임. 실제 함수는 src/rag_home_api/retrieval/hybrid_rrf.py의 search_hybrid_rrf임.
- 해당 함수는 keyword_query, semantic_query, top_k, filters 등을 받고 document를 담은 검색 결과 목록을 반환함. 공용 질문 분류·최종 응답 계약은 없음.
- origin/feat/SBC-rag-pipeline 24d32900715d0d301561e14f08ecf4c7093ac3ed에는 test/bc/lesson_pipeline.py의 build_retrievers·build_chain이 있음. 개인 실행용 파이프라인임.
- 담당 범위와 검색 메타데이터 계약이 겹치므로 이번 구현은 test/jh 안에 둠. 팀원 코드·공용 브랜치 연결은 합의된 진입점이 생긴 뒤 진행함.

## 개인 DEV·TEST 검색

- rag/run.py의 DEV·TEST는 Retriever(collection, law_only=True)를 선택함. 질문 분류 함수나 RunnableBranch를 호출하지 않음.
- BM25 문서와 PGVector 사전 필터를 법령 원문 category 및 LAW_ 문서 ID로 한정함. 가이드·공고는 법령 검색 대상에서 제외함.
- 청크·임베딩 색인을 재생성하지 않고 기존 jh_500/jh_1000을 사용함. 검색 결과의 ID·본문이 로컬 원문과 일치해야 법령 결과로 반환함.
- 기존 색인에 URL이 없으면 같은 ID·본문의 로컬 원문 메타데이터로 복원함. DB 메타데이터를 쓰거나 임의 법령명·조항을 생성하지 않음.
- 활성 평가셋은 law-qa-v1(9668e6aefbe8)이며 개인 DEV 10개·TEST 20개 모두 법령 전용으로 교체함. 이전 c3d4c4ead6cb 전체 문항은 비활성 보존본에 남김. 외부 전송 범위 확인 전 두 split의 실제 임베딩·모델 호출을 차단함.
- 이전 실험은 기존 해시로 보존하며 새 법령 검색 결과로 해석하지 않음.

## 서비스 입구 분류

- rag/law_router.py의 classify_question은 의도 표현과 임대차 맥락을 함께 확인하는 로컬 규칙임.
- 생활 말투의 인상 허용·수리 의무·퇴거·출입·신고 기한·감액 등도 법령 경로로 분류함. 단지명·공고 단어만으로 법적 질문을 비법령으로 밀어내지 않음.
- 공고·입주 자격·시설·가격·시세 등의 정보 탐색은 non_law로 전달함. 모호하거나 지원 범위가 확인되지 않으면 unsupported로 반환함.
- build_question_router에 기존 비법령 Runnable을 주입하면 원질문과 기존 반환값을 그대로 전달함. 핸들러가 없는 비법령 질문은 unsupported로 반환함.
- 분류 테스트는 DEV·TEST 평가 질문 파일을 읽지 않고 별도 경계 문장 36개를 사용함. 유한한 규칙과 경계 사례 검증이므로 일반 한국어 의도 분류의 정확도 측정은 아님.

## 법령 답변 계약

- build_law_handler에는 검색 Runnable과 생성 Runnable을 주입함. 이 어댑터는 외부 모델을 만들지 않음.
- 검색기는 검증된 법령 Document 목록을 반환해야 함. 생성기는 question과 documents를 입력받아 status, answer, cited_chunk_ids를 반환함.
- 답변 status는 answered 또는 insufficient_evidence임. 확인된 인용만 실제 검색 청크에 대조해 법령명·조항·공개 URL·원문 발췌와 함께 반환함.
- 근거 부족·빈 검색 결과는 고정 안내와 빈 citations를 반환함. 생성기의 임의 조문·인용은 근거 부족 응답에 붙이지 않음.
- 법령 외 문서·불완전한 출처는 생성 호출 전 거부함. 검색되지 않은 조문 인용과 검색·생성 오류는 error로 구분함.
- 인용의 구조·출처 연결을 검증함. 생성 답변의 의미상 정답 충족과 실제 모델의 사실성은 이번 오프라인 테스트에서 측정하지 않음.

## 합의 후 연결할 위치

- 팀의 질문 검증 후 search_hybrid_rrf 또는 build_chain을 호출하기 직전에 build_question_router를 연결함.
- 법령 분기는 아래 개인 법령 검색기를 사용함. 비법령 분기에는 팀의 기존 핸들러를 그대로 전달함.
- 팀 검색기의 filters와 메타데이터 형식은 담당자와 확인해야 함. 현재 팀원 브랜치의 벡터 필터 빌더는 doc_id 목록을 직접 지원하지 않아 개인 필터를 그대로 전달하지 않음.
- 공용 응답 DTO와 생성 출력 계약도 연결 전에 합의해야 함.

~~~python
from langchain_core.runnables import RunnableLambda
from retrieve import Retriever
from law_router import build_law_handler, build_question_router

# 실제 연결은 모델·데이터 전송 범위와 팀 진입점 합의 후 수행함.
law = Retriever("jh_1000", law_only=True)
law_search = RunnableLambda(lambda question: law.documents("B", question))
law_handler = build_law_handler(law_search, approved_generator)
question_router = build_question_router(law_handler, existing_non_law_handler)
~~~

- C에 연결할 때는 law.retriever("B")의 전체 후보를 기존 ContextualCompressionRetriever에 전달하고, 재정렬 뒤 law.verify_documents로 확인함. B 상위 5개를 먼저 잘라 C 후보로 쓰지 않음.
- 분류 경계 검증과 개인 DEV·TEST의 검색·답변 성능 평가는 각각 별도로 기록함.
