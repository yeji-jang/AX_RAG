## 2. 청킹 전략 비교 (최종 v1 데이터 기준)

### 2-1. 무엇을 바꿨나

- **재귀 단독 (`RecursiveCharacterTextSplitter`)**: 문단(`\n\n`) → 줄바꿈(`\n`) → 문장(`. `) → 공백(` `) 순으로 `650/80` 또는 `600/100` 분할.
  - 한계: 긴 마크다운 표가 중간에서 잘려 **두 번째 조각부터 컬럼 헤더(`| 단지 | 보증금 | 월세 |`)가 사라지고**, 표 바로 위의 소제목(`2. 임대대상 및 임대조건`)만 단독 초단문 청크로 떨어져 나옴.
- **구조적 + 재귀 하이브리드 (`split_text_structured`)**:
  1. **1층(구조 분리)**: 페이지 본문을 `일반 글 블록`과 `마크다운 표 블록(|...| + |---|)`으로 분리.
  2. **2층(블록별 분할)**: 일반 글은 `600/100` 재귀 분할, 마크다운 표는 **행 단위로만 분할**하고 잘린 모든 표 조각 맨 위에 **원래 헤더 2줄을 자동 재부착**.
  3. **3층(구조 보정)**: 표 위 소제목 등 `120자` 미만 단독 조각이 남으면 바로 다음 청크 앞에 병합.
- **공급호실 CSV 통합 (`load_housing_unit_chunks`)**: `open() + csv.DictReader`로 두 CSV를 조인해 1호실 = 1청크(327~526자)로 조립하고, `district`·`min_deposit_krw`·`min_monthly_rent_krw`·`exclusive_area_m2`를 선택 메타데이터(`| None`)로 분리 저장.

## 4. 오류·실패 기록 (지우지 않음)

> 단순 오타로 난 오류는 적지 않는다.

| # | 단계 | 무슨 일이 있었나 | 원인 | 어떻게 했나 |

  2. **STEP 5-B (`Versioned Cache`) — Cold vs Warm 차이 · 지연(`median`/`p95`) 해부 · 왜 즉시 채택(Keep)인가?**
     - **Cold Cache (`171642`, 적중 `0/10`) vs Warm Cache (`172134`, 적중 `10/10`)**:
       - **Cold (차가운 캐시, 최초 실행)**: SQLite(`data/cache/rag_cache.sqlite3`)가 `0건`으로 비어 있는 상태에서 10문항을 처음 질문하므로 **10건 모두 캐시 미스(MISS `0/10`)**가 발생함. 따라서 캐시 OFF와 동일하게 `PGVector + BM25 + KURE-v1 + LLM Re-ranking + LLM 생성` 전체를 끝까지 실행한 뒤, 정상 응답 10건을 SQLite에 새로 저장함.
       - **Warm (데워진 캐시, 재실행)**: 이미 10건이 저장된 상태에서 같은 10문항을 다시 질문하므로 **10건 모두 캐시 히트(HIT `10/10`)**가 발생함. DB 조회·GPU 임베딩·Reranker·Generator LLM 호출을 전부 건너뛰고(비용 **0원**) SQLite에서 즉시 꺼내 반환함.
     - **왜 Cold의 `median = 2,506.5ms`, `p95 = 8,008.6ms`가 높았나? (실측 10문항 오름차순 정렬)**:
       - Cold 10문항 정렬값(ms): `[64.8(03), 74.9(02), 77.0(07), 96.3(04), 104.8(08) | 4908.2(09), 5988.6(10), 7989.4(05), 8008.6(06), 21113.6(01·초기모델로딩)]`
       - **중앙 지연 (`median`, 50번째 백분위수)**: 오름차순 정중앙 5번째(`104.8ms`, 단일동 스킵)와 6번째(`4,908.2ms`, 다중후보 LLM 리랭킹)의 평균 = `(104.8 + 4,908.2) / 2 = 2,506.5ms`.
       - **`p95` 지연 (95번째 백분위수)**: 전체 중 상위 5% 느린 꼬리 구간(10개 중 9번째 = `8,008.6ms`). 첫 호출 모델 로딩 이상치(`21.1s`)를 제외하고도 사용자가 실제로 겪는 최악 체감 지연(복합 2구 리랭킹 8초)을 정직하게 보여줌.
       - **Warm 10문항 정렬값(ms)**: `[0.3, 0.3, 0.4, 0.4, 0.4, 0.4, 0.4, 0.4, 0.4, 0.8]` → **`median 0.4ms · p95 0.4ms`** (목표 `<100ms` 대비 **250배 여유**, Cold `p95 8,008.6ms` 대비 **20,021배 단축**!).
     - **100% 무손실 응답 일치 & 8대 안전성 게이트 PASS**:
       - Cold(`171642`)와 Warm(`172134`)의 10문항 전체 `retrieved_contexts` 및 `response` 문자열이 **바이트 단위 100% 동일(`same_resp=True, same_ctx=True`)**함을 검증함.
       - `test_cache_safety.py` 8대 게이트 100% PASS: 공백 정규화 일치(`hit 1.08ms`), 6개 버전/권한 축(`collection_name` · `index_version` · `embedding_model` · `llm_model` · `prompt_version` · `user_scope`) 변경 시 즉시 자동 무효화(MISS), TTL 만료 시 자동 삭제, `status="error"` 및 빈 응답 저장 거부(`set() -> False`).
  3. **STEP 5-C (`HyDE`, `optimize/hyde.py`) — 3중 출처 격리 설계 및 현 시점 미적용(보류) 사유**:
     - **동작 원리**: 구어체 사용자 질문으로 바로 벡터 검색을 하지 않고, LLM(`generate_hyde_document()`)이 먼저 *"정답 문서처럼 생긴 3~4줄짜리 가상의 실거래 요약 문서"*를 생성해 그 가상 문서 임베딩으로 DB를 검색하는 기법.
     - **3중 출처 격리 (`exp_03_rent_eval.py:307-327` · `optimize/hyde.py:49-66` `verify_hyde_isolation()`)**: 가상 문서는 LLM이 지어낸 가짜 수치(환각 보증금 등)를 포함할 수 있으므로 3겹의 방화벽으로 완전 차단함.
       1. **1중 — 검색 경로 격리 (Vector 전용 투입)**: `_search_single_plan(..., override_semantic=sem_override)`에서 가상 문서는 오직 **`semantic_query`(PGVector 임베딩)**에만 전달하며, **`BM25(keyword_query)`에는 원질문(또는 Rewrite 키워드)을 그대로 유지**해 가짜 수치가 키워드 매칭을 오염시키지 못하게 차단.
       2. **2중 — 파이프라인 생명주기 격리 (검색 직후 즉시 폐기)**: DB에서 회수된 **100% 실제 원본 청크(`candidates_12`)**만 다음 단계로 넘기고 가상 문서 문자열은 즉시 폐기. 따라서 **Re-ranker(C) · Generator LLM · 출처 인용(Citation)**에는 가상 문서가 1글자도 전달되지 않음.
       3. **3중 — 사후 자동 검증 격리 (`verify_hyde_isolation()`)**: 답변 생성 직후 가상 문서 앞부분 마커(`hypothetical_doc[:80]`)가 최종 `retrieved_contexts`(`context_isolated`)와 최종 `response_text`(`response_isolated`) 어디에도 포함되지 않았는지 자동 검사해 `hyde_isolated` 카운트로 로그에 박제함.
     - **현 시점 미적용(보류) 엔지니어링 판단**: 코드와 프리셋(`C_filter_rewrite_hyde`)은 구현 완료했으나, 현재 `KURE-v1 + Filter v2 + Query Rewrite` 조합만으로 `dev_v2`와 `test` 모두에서 이미 **`Recall@12 = 1.000`**에 도달함. 이미 검색 재현율이 100%인 상태에서 HyDE를 켜면 **추가 이득은 0인데 LLM 호출 지연(`+2~3초`)과 가짜 수치에 의한 벡터 드리프트 위험만 늘기 때문**에 본 도메인 최종 조합에서는 제외함(주로 사전 필터가 약하거나 추상적 개념 질문이 많은 법령·상담 도메인에서 위력이 큼).

       - **LLM-as-a-Judge (AI 채점관)**: 사람 대신 LLM(`gpt-6-luna`)에게 채점관 역할을 맡겨 답변의 충실도(`Faithfulness`)와 질문 관련성(`Answer Relevancy`)을 서술형으로 채점하는 방식. ID 기반 수학 공식(`Hit@5`, `Top1` 등)과 달리 확률적으로 문장을 분해·해석하므로 동일 답안지를 재채점해도 점수가 달라질 수 있음.
       - **소폭 변동 과적합 방지 + 육안 검수 병행**: 예를 들어 프롬프트 문구 미세 수정으로 `AR`이 `0.665 → 0.672 (+0.007)` 변했을 때, 이를 실제 성능 향상으로 착각해 점수 맞추기식 튜닝(과적합)을 하면 봉인 `test` 일반화 성능이 오히려 저하될 수 있음. 따라서 소폭 수치 변동만으로 판단하지 않고 **실제 생성 답변 원문을 사람이 직접 대조(육안 검수)**해 내용 개선 여부를 함께 확인한 뒤 최종 채택/기각을 결정함.
     - **엄밀한 해석 & 5가지 경계 명시**:
       1. **지표 성격 구분**: 진정한 결정론적(Deterministic) 지표는 ID 기반 검색 지표(**`Recall@12`, `Recall@5`, `Hit@5`, `Top1`, `MRR@5`**)뿐이며, 우리 러너가 사용한 **`LLMContextPrecisionWithReference`와 `LLMContextRecall`은 LLM 기반 지표**이므로 결정론성이 보장되지 않음(2회 모두 `1.000`으로 일관됐으나 일관성≠100% 정확성).
       2. **2회 관측의 통계적 한계**: 2회 반복 측정만으로 모분산이나 고정 오차 범위를 확정할 수 없으며, 위 수치는 **"바이트 동일 입력에서 관측된 점수 변동 사례(`F` 개별 최대 `0.500`, `AR` 개별 최대 `0.153`)"**로만 해석함.
       3. **`strictness=1` 설정 요인**: RAGAS 공식 기본값은 `strictness=3`(권장 3~5)이므로, `strictness=1` 환경에서 `AR` 변동이 증폭되었음을 함께 고려해야 함.
       4. **`Faithfulness` 원인 가설**: 사후 진단문·원문 대조에 기반한 유력 가설이며, 실제 RAGAS 내부의 Claim 분해 및 판정 원본 로그는 미저장 상태이므로 단정하지 않음.
       5. **발표·보고서 권장 요약 문구**: *"SQLite 캐시를 통해 검색 문서와 생성 답변을 바이트 단위로 동일하게 유지한 상태에서 RAGAS 반복 평가를 실시한 결과, 동일한 평가 대상임에도 Faithfulness는 개별 문항에서 최대 0.500, Answer Relevancy는 최대 0.153의 점수 변동을 보였습니다. 이는 시스템 출력 변화 없이도 LLM 기반 평가 과정에서 측정 변동이 발생할 수 있음을 보여주는 사례이며, 이에 따라 결정론적 검색 지표·반복 평가·답변 원문 육안 검증을 병행하는 평가 전략을 채택했습니다."*
